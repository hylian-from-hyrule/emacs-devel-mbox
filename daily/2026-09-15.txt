>> But, as for the completion-ignore-case, I tend to lean towards filtering
>> for KIND in the completion-table rather than via the predicate.
> For this particular one, it was the choice between adding a new argument to
> an existing generic function and adding a new generic function (with
> a default implementation returning nil).

You mean adding an `&optional kind` argument to
`xref-backend-identifier-completion-table` vs defining a new
`xref-backend-identifier-completion-predicate`?

While the current choice works fine in many cases, I think it's
fundamentally fairly problematic because you'd rather use very different
completion tables when completing say some module/library/package/unit
name (where you may want to consult the local filesystem) vs completing
some variable name.

The predicate can filter things after the fact but it can't influence
how the completion table works, so it forces the completion table to
collect&return the kitchen sink.

place that has information about each candidate.

Thanks, I reproduced this problem on HEAD and emacs-gtk3.

CC'ing Eli for comments.  I'm not very familiar with the composition
system.  Please correct my misunderstandings.

I did some investigation:

- on the first bad commit (80383d8e57e) the Emoji sequence 263A FE0F
  goes through the Emoji path in auto-compose-chars (i.e. the first
  branch of the cond expression).  It is recognized as an automatic
  composition as a whole.

  The sequence is shaped in auto-compose-chars using either
  compose-gstring-for-graphic (on GUI) or compose-gstring-and-emoji (on
  TTY).

- on the last good commit (b33d4088a66) the Emoji sequence 263A FE0F
  goes through the non-Emoji path in auto-compose-chars (i.e. the third
  branch of the cond expression).

I find this quite surprising.  On both commits, the composition is
produced by compose-gstring-for-graphic.  The only difference I can
think of is that, on the good commit, the composition seems to be
produced by this rule

    ELISP> (char-table-range composition-function-table #xFE0F)
    (["\\c.\\c^+" 1 compose-gstring-for-graphic]
     [nil 0 compose-gstring-for-graphic])
    ELISP> (string-match "\\c.\\c+" "\x263a\xfe0f")
    nil

On the bad commit, autocmp_chars is called with ch=0x263A.  But on the
good one, autocmp_chars is called with ch=0xFE0F, and 0xFE0F is
considered the emoji script:

    ELISP> (char-table-range char-script-table #xfe0f)
    emoji

Therefore, it goes through the Emoji font selection path in font_range
(in font.c), instead of picking the font based on the first codepoint.
This can be confirmed with a simple change in font.c that fixes this
problem:

modified   src/font.c
@@ -3902,7 +3902,7 @@ codepoint_is_emoji_eligible (int ch)
     return true;

   if (! NILP (Fmemq (make_fixnum (ch),
-		     Vauto_composition_emoji_eligible_codepoints)))
+		     Vauto_composition_emoji_tty_eligible_codepoints)))
     return true;

   return false;

[ What I don't understand here: if the Emoji sequence is known to be
  composed due to a specific font (e.g. Noto Color Emoji), why would it
  go through another round of font selection (based on the first
  codepoint and/or heuristics around the emoji script) at all? ]

Given my current understanding, I think it's OK to merge
auto-composition-emoji-tty-eligible-codepoints and
auto-composition-emoji-eligible-codepoints: codepoint_is_emoji_eligible
is called on the first codepoint that resulted in the composition (which
used to be FE0F for many Emoji sequences).  And since we added more
rules, we should consider them here, too.

I quickly tested the change above on emoji-test.txt and
emoji-zwj-sequences.txt, and it didn't introduce regressions on both GUI
and TUI as far as I see.

Eli, what do you think?  I can prepare a patch if you agree with this
approach.

> I'm asking how to write a predicate that needs to filter by KIND, when

KIND is already available to the predicate function because it's 
lexically captured. In this example

     (cl-defmethod xref-backend-identifier-completion-predicate
         ((backend FOO) &optional kind)
       (lambda (candidate)
         ... body ...))

<body> can reference KIND (the argument for the cl-defmethod) and return 
t if CANDIDATE has at least one definition belonging to KIND.

To describe the next step, here is a very naive implementation: switch 
to the completion table's file buffer. Then loop across the buffer, 
finding the lines that contain definitions for CANDIDATE. On each line, 
look around to determine whether this definition is of the needed KIND 
(using a regexp, most likely), and if it does, exit early and have the 
predicate return t. If the search reaches the eob, return nil.

This is likely slow, but if there is, for example, a way to build a 
regexp that searches for definitions of only this KIND, that would be 
faster (this seems feasible for e.g. DEFUNs, but not in general).

A second approximation of a "fast" solution would be to do one pass 
through the tags buffer and collect all completions of KIND into a hash 
table. Then the predicate could do lookups in it instead, exchanging the 
complexity for an upfront computation.

It might necessarily be an improvement if the scan itself is slow enough 
(because otherwise IIRC the predicate is used "lazily"). But it's 
something to try anyway.

Stallman's test is: could you, in principle, do this computing activity 
entirely on your own computers with free software, without communicating 
with anyone else's computers? If yes, the activity is "your own 
computing," and doing it via someone else's server is SaaSS — an

Let me give my opinion:

Thanos's implicit argument is:

- hermes.el can use a local model.
- Therefore hermes.el is not SaaSS or wish to say there is no problem to 
users
- Therefore there is no objection specific to hermes.el.

Step 3 does not follow. A program can be free and non-SaaSS while still 
being a vector that normalizes and routes users into SaaSS. Stallman's 
essay anticipates exactly this move:

"Some web pages install nontrivial, even large JavaScript programs into 
your browser without informing you. When these JavaScript programs are 
nonfree, they cause the same sort of injustice as any other nonfree 
software."

And more directly, on services with mixed features:

"Some sites offer multiple services, and if one is not SaaSS, another 
may be SaaSS."

The point: the presence of a free/non-SaaSS path does not neutralize the 
harm of the SaaSS path being the default, the advertised, or the path of 
least resistance.

The availability of a free path does not excuse a service whose normal 
use is unjust. The same logic applies here: the fact that hermes.el can 
be pointed at a local model does not address the fact that the Hermes 
project's normal, documented, advertised use routes through Nous Portal 
— a SaaSS provider with undisclosed training data.

And about ellama as a precedent: it's in GNU ELPA and also supports 
multiple providers, including proprietary ones. But this is not a 
defense — it's an admission that the same problem already exists 
elsewhere.

Yes, this is correct.

The reason is that we want codepoints like U+263A to be shown in their
standard text-style appearance when they appear alone, but we want
them shown in emoji-style when they are followed by VS-16 (U+FE0F).
This precludes making these characters belong to the emoji script,
especially since we usually prefer to show such symbols in their
text-style using the default font (which usually supports quite a few
of them).

So if the above changes somehow caused the GUI display to have Emoji
composition rules in the slots of composition-function-table that
belong to the U+263A and similar characters, this is wrong, and should
be undone.  The trick in font.c which uses font_range to force Emoji
font when these codepoints are followed by VS-16 must not become
broken, because it's there to support this dual-style display of those
symbols.  Instead, we should do this only for TTY frames, because
there Emacs doesn't select fonts, and thus we don't care about these
subtleties, leaving them to the terminal emulator

Instead of relying on these environment variables, I think a better
solution would be to first try opening a connection to the display server
and, if that fails, fall back to text mode.

Currently, the PGTK build requires a working graphical display, and exits
if none is available. The exit(1) call happens in gtk_init(), which is
called by pgtk_term_init(). The gtk_init code is accompanied by the
following comment.

 * This function will terminate your program if it was unable to
 * initialize the windowing system for some reason. If you want
 * your program to fall back to a textual interface you want to
 * call gtk_init_check() instead.

Thus changing the code to call gtk_init_check instead would avoid the exit,
but forcing Emacs to switch to text mode requires a larger refactoring than
that.
