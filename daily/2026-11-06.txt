> Please at least wait until there's some sign of something like that

> happen, or are happening already due to a variety of real-life

i won't rehash the point more, but the word “threat” here is incorrect,
though i understand it can seem that way from your perspective.

it isn't a threat, nor negotiation, nor point of debate. it is a
statement of intent; a fact, as much as any human intention can be fact.

the ground does not threaten the rain with getting wet, it simply does.

in my view, it was posted to this list, not as a threat, but as a
signpost: should the land become hostile, here is a place we can gather,
here is a place we can support each other. there's no better place to
post that than where we all already gather.

i would like you to consider another point of view, that is obvious to
me, but maybe not to you: while no one here wants a fork, it is
primarily the people who use human emacs that will suffer for it, at
least in the short and medium term. it is human emacs that will be
rejecting improvements that gnu emacs will accept, while gnu emacs will
have no issue with taking any patches to human emacs to improve gnu
emacs.

while we will all suffer collectively for a substantial fork, gnu emacs
will suffer less, with a larger community, recognition, and the ability
to accept some contributions that, regardless of quality, human emacs
will not be able to accept.

so, though the greater burden will be on the maintainers and users of
human emacs, the signatories and other participants have decided that
that is a price we must pay in order to abide our sense of morality and
justice. this is the very same decision making that birthed free
software itself; a proud tradition that is worthy of being upheld as the
world has changed around us and demanded we accommodate those changes in
our unending pursuit of human liberty, of which free software is but one
part in support.

> And I'm most alarmed by the suggestion that we should reject someone's
> code based on something that is unrelated to the code itself.  This is
> a step along a slippery slope that I very much hope we will never
> take.  Because the next thing we will be requested is to reject code
> of people with particular views or opinions, or people living under
> certain regimes, etc. etc.  We never did anything like that, and
> IMNSHO we shouldn't, ever.  The world out there is full of grave
> problems that need to be solved, but Emacs development is not the
> right place to solve almost all of these problems.

gnu emacs already rejects code for a number of reasons outside the code
itself. copyright assignment has already been mentioned, but you can
also see recent discussions about things in elpa potentially promoting
non-free software services. in the past, code has been rejected because
it provided features for non-free platforms that weren't available on
free ones. and so on. so gnu emacs rejects software for ideological
reasons rather than technical. i think that's a fine way to
be. technical details should always be in support of the social goals,
and, indeed, can't be separated anyway.

slippery slopes are dangerous, but the solution here, as in most things,
is constant vigilance, to make sure our beliefs are being upheld in the
constant work of creation and maintenance.

-bjc

I think you misunderstand the main difficulty in adding this feature
to Emacs.  The main difficulty is to modify and/or reconcile the
current assumption that all screen lines (a.k.a. "glyph rows") on TTY
frames have the same height whose "pixel height" is taken to be 1.
This assumption is fundamental in all the TTY display code that deals
with layout and anything that depends on the layout: vertical cursor
movement, support for mouse, TTY menus, and much more.

What you suggest doesn't by itself solve this fundamental problem,
because image slices are just images: they still need to be laid out,
each slice on its screen line.  In your diagram above, there's nothing
to the left of the slices, which is impossible in Emacs without some
magic (which is currently missing).  Suppose that a buffer's text is
like this:

  abcde <IMAGE> xyz

Then, I presume you would want to display this as slices like this:

        | image band 1   |
        | image band 2   |
        | image band 3   |
        | image band 4   |
        | image band 5   |
  abcde | image band 6   | xyz

Is that right?  In that case, the empty space to the left of all the
slices except the last (bottom-most) one is a problem for the Emacs
display engine, because there must be something there for us to be
able to tell the terminal to show those slices.  We must write
something, probably space characters, to the terminal from the left
edge of the window till the beginning of the slice.  And we can only
write those space characters if the corresponding glyph row has some
glyphs there.  Those glyphs should probably be generated by the
display code itself, because they don't correspond to any buffer text,
but some code needs to be added to do it, and that code must be part
of handling text with embedded images.

In addition, with slices we will have hard time calculating the pixels
in a way that will avoid gaps between slices on the screen.

So I think we need either some additional tricks, like an ability to
generate more than one screen line for a text line with embedded
images, or do what Gerd suggested back in 2022: abandon the simplistic
layout of TTY frames and teach Emacs to support variable-height glyph
rows on TTYs.

In both cases, I'm afraid it is not a trivial job, and will require
studying the current display code and making non-trivial changes in
it.  If you or anyone else are up to the job, I personally and others
will be happy to provide advice and guidance.

3 supported ways to display images in the terminal (I would not be 
surprised if there were more): Sixel which is old and widely supported 
by VTxxx terminals, Kitty Image Protocol which is popular because of 
Kitty Term, and Kitty Unicode Placeholders which is a second way Kitty 
Terminal deals with images which is what I think Ron Li is thinking of.

As far as I can tell, Sixel and Kitty Image Protocol are similar in that 
they blat out bits to display in the TTY.  The pixels stay on the TTY 
screen, some TTYs scroll them around.

The Kitty Unicode Placeholder is different.  The image is "uploaded" to 
the terminal once and each character shaped block of the image is 
identified with a Unicode character: U+10EEEE, encoding the image ID in 
the fg color. The row and column values are encoded in the diacritics.  
Thus each cell (each character sized block of the image) has a unique 
unicode "character" which, when emacs wants to tell the terminal this 
character sized block of the image goes here, it sends that unicode 
character to the terminal and the terminal outputs the intended block of 
the image.

But the thing I want to get across here is that all of these things are 
how to display images in a terminal.  If you are mixing images and text, 
that's a different problem.  If you have some file like some mime 
document with embedded images, then I think you need some mode in emacs 
that deals with those file types (maybe it exists already?) that when it 
shows the image part of the file it outputs the image bits in sixels or 
kitty graphics, or, it first uploads the image to the terminal using the 
kitty placeholder and then outputs kitty unicode placeholders where it 
wants to output those cells with images.

If you know that a cell in the glyph matrix has a part of an image and 
in Ron's case, a strip of cells, you want to output that portion of the 
image to the terminal using whatever image protocol it supports.  A 
strip is a good thing rather than many individual cell sized blocks, 
it's more efficient.  Even better would be a rectangle but that's a 
further improvement.

At least, this is my understanding!

> There are 2 separate things: 1) displaying graphics in a terminal window 
> and 2) displaying files with embedded images or files which are an

These two cases are identical from Emacs's POV.  An image is
represented in an Emacs buffer as a special 'display' property, which
shows the image instead of the text which has that property.  Showing
a single image in a buffer is thus a special case of showing an image
embedded in text: in the former case you have only the text covered by
the 'display' property, in the latter case you also have text without
the property before and after the image.

The important aspect of this is that in both cases the Emacs display
engine needs to be able to lay out the text and the image in a way
that what's on the glass corresponds to what Emacs holds in its glyph
matrices.  This is needed so that Emacs could do stuff that requires
the layout information.  For example, C-n needs to compute the buffer
position on a screen line below the current one, and processing a
mouse click needs to determine the buffer position at the click point.

> I think Ron is talking about the display engine in emacs that would 
> convert the image to whatever the terminal supports.  There are at least 
> 3 supported ways to display images in the terminal (I would not be 
> surprised if there were more): Sixel which is old and widely supported 
> by VTxxx terminals, Kitty Image Protocol which is popular because of 
> Kitty Term, and Kitty Unicode Placeholders which is a second way Kitty 
> Terminal deals with images which is what I think Ron Li is thinking of.
> 
> As far as I can tell, Sixel and Kitty Image Protocol are similar in that 
> they blat out bits to display in the TTY.  The pixels stay on the TTY 
> screen, some TTYs scroll them around.
> 
> The Kitty Unicode Placeholder is different.  The image is "uploaded" to 
> the terminal once and each character shaped block of the image is 
> identified with a Unicode character: U+10EEEE, encoding the image ID in 
> the fg color. The row and column values are encoded in the diacritics.  
> Thus each cell (each character sized block of the image) has a unique 
> unicode "character" which, when emacs wants to tell the terminal this 
> character sized block of the image goes here, it sends that unicode 
> character to the terminal and the terminal outputs the intended block of 
> the image.

You are talking about how to deliver the image data to the terminal.
That needs to be implemented, of course, but it isn't the main
difficulty.  The main difficulty is to adapt the text-mode display
code to this situation, because images are rarely the same vertical
size as the characters shown on the terminal.

> But the thing I want to get across here is that all of these things are 
> how to display images in a terminal.  If you are mixing images and text, 
> that's a different problem.

Not in Emacs, it isn't.  It's the same problem.  Emacs still needs to
know the dimensions of the image on the glass, because otherwise Emacs
features that users expect to work with images will not work.

> If you have some file like some mime 
> document with embedded images, then I think you need some mode in emacs 
> that deals with those file types (maybe it exists already?) that when it 
> shows the image part of the file it outputs the image bits in sixels or 
> kitty graphics, or, it first uploads the image to the terminal using the 
> kitty placeholder and then outputs kitty unicode placeholders where it 
> wants to output those cells with images.

Again, you are talking about how to deliver the image data to the
terminal, whereas I'm talking about the layout calculations in the
presence of images.

Emacs maintains a data structure called "glyph matrix" for every
window on display.  That data structure is a 2D array of objects
called "glyphs"; each glyph describes a single "display element" on
the glass.  A display element can be a character, an image, a
composition (result of composing several characters, like a base
character and a diacritic), a stretch of white space, etc.  Each row
in the glyph matrix describes a single screen line.  To perform layout
calculations, Emacs needs to know the Y-coordinate of each glyph row
and the width of each glyph.  Currently, the text-mode display assumes
that each glyph has 1-pixel width and row number N (zero-based) has Y
coordinate equal to N.  Displaying images means these assumptions
cannot be true anymore.  The width issue can be handled relatively
easily (we already do something similar for wide characters that
occupy 2 columns on display).  The height issue is harder, because the
display code currently cannot generate several screen lines (= glyph
rows) from a single display element.

I hope the above explains what I think is the most complex part of the
job of adding image support to TTY frames.  If not, feel free to ask
questions.

If you hand-translated Hunspell version X into Elisp and then version
Y were released and you wanted to update your Elisp translation, what
would the workflow be?

1. You read the diffs. Maybe not the whole diff X..Y; maybe you read
individual commits, or short patch series. You work out what they did
and how they did it.
2. Knowing your translation, you work out how to implement the changes
on top of it.
3. You run tests. Fix code until they pass.
4. You commit and push.

The LLM-assisted workflow is essentially the same. “Hey agent. ! git
-C ../hunspell log X..Y. Explain those changes to me.” The agent then
generates a bunch of tool calls to read the changes, read the context
around them, gives you the code tour. “Now let’s port those changes to
our ./vibespell.el.” Reads the existing implementations, modifies the
existing implementation, runs tests, until convergence. “Done, tests
pass.” You review the changes, “Hey, this chain of (nth …) accesses
would look better as a pcase”. — “You’re right, changed, tests pass.”
You commit and push.

I am convinced now that we must distinguish between source code that
happened to have come originally from an LLM, and non-source code in
high-level-language, used as an intermediate form generated by an LLM
from source code in some other form.  These are fundamentally
different scenarios and we need to treat them separately.

In the former case, the one-time use of the LLM has no effect _on
further development_, since people working on that code won't have a
reason to care about the LLM.  (The LLM's use _can_ have an effect _on
legal issues_.)  The code needs comments and clarity sufficient for
humans to work on it.

The latter case is like Bison output, where the Bison input is the
source code.  Using such source code is acceptable because Bison is a
released free tool, not limited to use as SaaSS, and acceptable to
require developers to use.  Using LLM input as source code will
require that the specific LLM be free, released, and usable locally,
and acceptable to require developers to use.

This issue is separate from the issues of copyright that LLMs
inherently raise.  We need to heed both issues, but the kinds of
requirements they imply will be different.
