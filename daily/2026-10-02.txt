I'd like to propose ebuild-mode for inclusion in NonGNU ELPA.

This collection of modes will help the user to efficiently write and
edit ebuilds, eclasses and other files that are specific to Gentoo,
a meta-distribution with various targets (GNU/Linux distribution,
prefixed environments in other operating systems, and integration
of other kernels and userlands like the BSDs or the GNU Hurd).

Ebuilds describe the build process and dependencies of a software
package to compile and install it automatically under the control of
a package manager.  They are simple text files based on Bash scripts.
Eclasses are comparable to libraries providing generic functions that
ebuilds can use by sourcing the eclass on request.

The package provides:
- ebuild-mode and ebuild-eclass-mode: major modes to edit the above
  two file types, with font-lock syntax highlighting, completion of
  package manager and eclass function names, KEYWORDS manipulation,
  creation of new ebuilds from a skeleton, and interfaces to Portage,
  pkgdev and pkgcheck.
- ebuild-repo-mode: minor mode for files in an ebuild repository;
  sets up some editing conventions like tab-width, fixes whitespace
  and updates copyright years on save.
- devbook-mode: editing the Gentoo Devmanual (DevBook XML).
- gentoo-newsitem-mode: editing GLEP 42 news items.
- glep-mode: editing Gentoo Linux Enhancement Proposals (GLEPs).
- ebuild-mode.texi: Texinfo manual.

Repository:
- Git clone: https://anongit.gentoo.org/git/proj/ebuild-mode.git
- Gitweb: https://gitweb.gentoo.org/proj/ebuild-mode.git/

Authors: Matthew Kennedy, Diego Pettenò, Christian Faulhammer, Ulrich Müller
Maintainer: <emacs@gentoo.org>
Contents: multiple files
Version: 1.87 (tagged as ebuild-mode-1.87 in Git)
License: GNU General Public License, version 2 or any later version

Dependencies:
- GNU Emacs 26.3 or XEmacs 21.5.35
- no other dependencies on Emacs Lisp packages
- optionally uses tty-format (https://user42.tuxfamily.org/tty-format/)

The package byte-compiles without any errors or warnings and passes
all its tests on Emacs 26 to 31, Emacs from Git, and XEmacs 21.5.

ebuild-mode was first released in 2006 and is widely used by Gentoo
developers.  It is distributed in Gentoo as app-emacs/ebuild-mode
(and app-xemacs/ebuild-mode), and I have maintained it since 2007.

Any feedback about the package is welcome, in particular about any
changes necessary before inclusion in NonGNU ELPA.

Thanks in advance,
Ulrich

The code looks good, my main points would be:

- In ebuild-mode.el to add an explicit an

  ;; Package-Requires: ((emacs "26.3"))

  pseudo header, so that package.el can pick up on the minimum version.

- You can drop all the :group annotations for the user options, since
  they follow a defgroup declaration.

- Some of the regular expressions seem fairly involved, I think it would
  be more readable in rx notation.  You can use the "xr" package to
  translate existing regular expressions to rx btw.

- If you don't want to write compatibility code for `static-if', you
  can also add a dependency on (compat "30").  This will only install
  the dependency if is actually necessary to do so.

- You have some trailing parentheses, like after the static-if
  definition.

- Using (kbd "C-e") instead of "\C-e" would be more conventional and
  what I think most users are used to if they read the source code.

- You have some instances where you build commands using something like

    (format "ebuild %s %s" file command)

  Shouldn't you wrap file in `shell-quote-argument', in case it includes
  spaces or some meta-charachters?

- If you want to exclude any files from the tarball, add an .elpaignore
  file that describes what files to exclude.

Other than that, I don't think there are any issues.  The package builds
cleanly (I've attached a tarball I managed to build locally), so I'll
add it to nongnu.git as soon as I am sure that you want everything in a
single package.

The ELPA build server will look back in the history for the last commit
if can find that bumps the ";; Version:" header in the main file.  So if
you don't bump the version after pushing the changes, ELPA will not

Since no one else seems to have an opinion on this, I guess I'll make a 
decision. :)

There are two things to decide on: first, how should the hook work? I 
think Stefan's suggestion is reasonable:

> Another option is to store the DOM in a var and let the hook functions
> change it by side effect.

As he mentions in his message, it's not the most pure-functionally 
elegant, but it's probably simpler. EWW already stores the DOM in the 
:dom property of 'eww-data'. Another benefit I see with this is that the 
hook can be used to do other things as well.

The second question is when the hook should run. If we go with modifying 
the DOM by overwriting :dom in 'eww-data', then we probably want to run 
the hook shortly after we parse the HTML, and (I think) also after we 
call 'eww-readable-dom'. I'd recommend doing this in 'eww-display-html' 
and 'eww-readable', since those are the places we parse the HTML. (You'd 
have to move the '(plist-put eww-data :dom document)' call in 
'eww-display-document' to those functions too, but I think that's a good 
idea because it consolidates where we write to 'eww-data'.)

It'd also be nice to call this before we display other content types. I 
think the relevant functions are 'eww-display-pdf', 'eww-display-image', 
and 'eww-display-raw'.

As for the name of the hook, I'd go with 'eww-before-render-hook' for 
symmetry with the existing 'eww-after-render-hook'.

Of course, if you or anyone else have different ideas, I'm all ears. I 
don't have a strong preference here, and am really just making a 
decision so a decision gets made. :)
