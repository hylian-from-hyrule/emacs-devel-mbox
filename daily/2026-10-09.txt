The variable backup-by-copying-when-privileged-mismatch
preserves the ownership of files with low user or group id
(e.g., root-owned system files).  Its current range for
deciding what ids are in the system range is 200 and below.
I think this boundary is too low for modern systems.

Systemd uses ids 1-999 for system services.

Various GNU/Linux/Unix user-creation tools I looked at
(adduser and useradd) create user accounts starting with
id 1000 or 1001.

macOS starts numbering regular users with id 501.

MS Windows starts regular users accounts with id 1000.

Based on these data, I conclude that
backup-by-copying-when-privileged-mismatch
should be increased to this:

  (if (eq system-type 'darwin) 500 999)

Note that backup-by-copying-when-mismatch is t by default
anyway, and backup-by-copying-when-privileged-mismatch
then has no further effect.

What do other people see on their systems?  Does anybody
have regular user or group ids low enough that this change
would break you?

 < Stephen

Adding Paul to this discussion.

backup-by-copying-when-privileged-mismatch is a defcustom, so why do
we need to discuss its default value? just customize it to a different
value if it doesn't fit your needs, and move on.

As for the default value, I think the important question is not where
the "privileged" IDs end, but whether an ID higher than 200 is
frequently enough assigned to privileged accounts, and what are those
accounts.  If exceeding the value of 200 is relatively rare, the
current default is still OK, IMO -- as the default.

Hi,

please find attached two Gnus/IMAP/SMTP patches.

The first simply changes the order of ports 25 and 587 to nudge 
users
towards port 587. (Some servers support both, but allow 
authentication only on 587. On those servers the code would 
incorrectly assume that authenticating was pointless or 
impossible, and then fail to send mail unless the user knew more 
than most. On other servers this change makes sending mail 
slightly faster or slower.)

The second patch is much larger, and adds support for RFCs 6530-3, 
9755 and parts of 9051 as a side effect. FWIW 6530 is now 
supported by the servers for 70-80% of internet users, including 
the biggest two, gmail and o365.

I've been using versions of these patches since 2023. The 
attachments are newly rebased to 32.0.50, though.

Thanks in advance for any comments.

Arnt
