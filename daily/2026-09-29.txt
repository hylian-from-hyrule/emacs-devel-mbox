> >> When it’s the user’s responsibility is the second part of my reply: If
> >> it is the user’s responsibility to choose once there’s a free
> >> alternative in the list, then there’s no reason for the many fixes
> >> that we do in Free as in Freedom distributions:
> >
> > Once again, you've lost the context: the user's responsibility starts
> > where ours ends.  I submit that our responsibility ends beyond the
> > first leg: we don't show any nonfree alternatives in our programs, but
> > if a non-GNU free program allows that, it's the user responsibility
> > not to choose it.
> 
> Would that mean that I could promote proprietary software by splitting
> it into a proprietary server and a free client and then writing an Emacs
> mode that uses the free client to connect to the proprietary server?

No, because the free client must allow the user to use free services
in a reasonably easy way.  It cannot force the user to use only
nonfree services.

> How much choice would I have to add to get accepted?

Just one free alternative is IMO enough, if selecting and using it
doesn't require any jumping through hoops.

> How far could I restrict user choice without risking exclusion?

If by "restrict" you mean not allow the user to use free services, you
cannot.  Such a client will not qualify for being supported by Emacs.

> > It is possible that we do unnecessary stuff elsewhere, but that
> > doesn't affect my opinion.  Doing more is okay, but should not be a
> > mandatory requirement.
> 
> This is why this discussion is impactful: if parts of what GNU
> maintainers do is unnecessary (patching retroarch, excluding minigalaxy
> from Free as in Freedom distros, patching out optional blobs from Linux,
> …), this may affect a lot of communities outside Emacs.

Such a discussion should be conducted in a different forum, not here.
We have enough noise here discussing just Emacs.

> Agreed: Hermes recommends the unfree option.
> 
> It doesn’t pro-actively show popups or unhappy clippy’s if you use
> something else, but it lists it as recommended option in the setup.

Probably because lazy people will find it the fastest.

> The relevant rule is written explicitly: “Programs in the system should
> not suggest installing nonfree plugins, documentation, and so on.”
> 
> With Hermes Agent there is one more level of indirection, but there is
> no choice in the first step:
> 
> The packaged program (hermes.el) only works with a specific free
> software client (no choice there: you must use this client) that
> recommends a proprietary SaaSS platform.

That is true, but since the Hermes agent is not part of Emacs and is
not a GNU program, we cannot be held responsible for what it does.  We
are only responsible to verify that it allows use of free services in
a reasonably simple way.  Why should we be responsible for anything
beyond that?

And anyway, how will this work in practice?  If any level of
indirection is our responsibility, the process of deciding whether a
package can be put on ELPA becomes tremendously complex and expensive.
It is no longer enough to review the package's code and the external
programs and sites it communicates with (which can be done without
ever installing nor running anything except Emacs).  No, we will now
have to actually install the dependency programs or go out to all of
the Web sites with which the package communicates, review their
installation and configuration processes, make sure none of the
alternatives in these processes could ever be nonfree (e.g., does a
comment in a sample config file that mentions some nonfree site or
program constitute "steering" users?).  If the dependency has another
dependency, we will now have to install, configure, and review it in
turn, and then do the same with its dependencies, etc. etc.  Who will
be able to do all that?  We are falling behind in reviewing submitted
packages already, even without all that.  It's simply unreasonable to
expect us to do all that.

IOW, accepting these too-strict criteria makes maintaining ELPA
impractical.  People will stop submitting packages to us and will
instead submit them to MELPA, thus undoing all of our efforts during
the recent years to create an ELPA that users can trust.  Is that what
we want?

> > Emacs is not a complete distribution, unlike Trisquel and others.  So
> > what they do is not necessarily relevant to what we should do.
> 
> What Emacs does may be relevant to them, because Emacs is at the core of
> GNU and is the program with which GNU started.

Maybe so, but that's not the focus of this discussion, though.

There are two issues here.

1. Discussion on github:

  > Discuss that over here https://github.com/ahyatt/llm/issues if you have
  > objections.

One of the GNU Coding Standards says that the maintainers should be
reachable by email.  Using a Github discussion forum requires making a
Github account and that requires running nonfree software.  We
maintainers, of any part of GNU Emacs, must not tell users to run a
nonfree program to talk with us.

See https://www.gnu.org/philosophy/whats-wrong-with-github.html for more info.

2. Referring to other programs and services.

                 emacs-devel is not the right place to complain about an ELPA
  > package.  Package authors are responsible for their own packages.

Package developers are responsible for the technical issues about those
packages, but this is a global issue about Emacs including its packages.

Basically, there are two policies we could reasonably follow about
packages that use nonfree LLMs (which is, more or less, all LLMs):

* They are ok provided they support only the LLMs that are very well
known, which is allowed based on the same rule that permits
`browse-url-chrome'.

* Those LLMs are so disgusting we should make an exception to that rule
and not support any LLMs at all.

There are serious arguments against each, but I don't see any better
alternative.

I don't think we should rush to change this policy.  For now, we can
continue with the practice of accepting those very well known LLMs,
but keeping in mind that there is a moral issue there.

I've now installed on the master branch the implementation of
xref-find-by-kind for the 'etags' backend.  It includes some
(hopefully) improvements to the doc strings.

Completion, as implemented for this backend, is very slow, especially
if you type only a small portion of the identifier's name.  That's
because it has quadratic behavior: for each candidate, it examines all
the possible completions, and filters the candidate out if none of the
completions match KIND.  If you type nothing and just press TAB, it
will take forever for a large enough project (such as Emacs).
Improvements are welcome.

I couldn't come up with a better idea, because the only way etags.el
can know the KIND of a candidate is by retrieving its full xref-item,
whereas the candidates passed to the predicate are just the identifier
names, without any auxiliary information.  I considered the
possibility of tweaking xref-backend-identifier-completion-table so as
to include in each candidate enough meta-data to allow its filtering
by the predicate, but decided against that, because doing so would
slow down the completion of 'M-.', and I didn't like that.

Disabling the filtering predicate is possible, which makes completion
much faster, but then there's a real danger to mistakenly type a name
of an identifier that doesn't match the selected KIND, which then
signals an error saying there's no such identifier of that kind.  I
don't know what is worse.

Finally, there's one annoyance with this when using it in the Emacs
tree: once a reference is found in a Lisp file, the next "C-u M-g M-."
will use the elisp backend, and thus show you a completely different
list of "kinds".  The only way to work around that is to turn on
xref-etags-mode in every buffer (via find-file-hook or similar), and
I'm guessing that Dmitry will say it's by design.  But maybe a nicer
solution could be found for this particular case (or for Xref in
general)?
