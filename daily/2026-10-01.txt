  > Nonetheless, having an alternative in a menu is neither "steering" nor
  > "promotion", because promoting an alternative needs to explicitly and
  > actively describe it in favorable terms, not just show it.

Marketing promotion typically does try to present an alternative in
terms of praise, but not necessarily.  Some promotional activities aim
only to make people aware that something exists, or lead them to dwell
on its name for a moment.  Either way, the effect is to promote the
uptake of that product, as marketers know.

What I mean by "promoting" a program or service is doing anything that
suggests (even implicitly) that we encourage people to use it -- that
it is a good thing to use.  That includes making users aware that it
exists.  If we do something that promotes an unjust program or
service, we encourage it to be used by (and to mistreat) more users
and we associate ourselves with that promotion.

We could also describe this as "mentioning to the users" that program
or service.

  > The words we use don't matter, as long as we agree that doing so does
  > not disqualify a non-GNU free program that Emacs communicates with.

You and the GNU Project very much disagree about this point.  Whether
hermes.el references the Hermes agent is out of our hands.  However,
whether GNU Emacs refers to hermes.el is the GNU Project's decision.

Including hermes.el in ELPA means Emacs refers to / promotes /
recommends / mentions hermes.el in a very strong manner.  That can't
avoid encouraging Emacs users to use the Hermes Agent and its
configuration program, because using hermes.el leads almost inevitably
to using the other two.

Given those circumstances, the GNU Coding Standards say that a
reference to something nonfree from the Hermes Agent counts as a
reference from hermes.el.

Hermes Agent refers to / promotes / recommends / mentions Nous in a
very strong manner, and Nous implies use of various nonfree and SaaSS
LLMs; I think all of them are non-free.  (Shall we call it "Noose", as
in "Not recommended to put it around your neck"?)  Anyone who starts
using hermes.el will probably be led to one of those LLMs.

The message of that chain of reference contradicts our principle
message to the public, so we should break that chain of promotion.

Eli, this is the crucial point where you have misunderstood the
GNU Project standards about referring to nonfree programs.
The misunderstanding is not about the Hermes agent in particular,
but about the standards themselves.

Given a free program P1, whether it is ok for a GNU package to
reference / recommend / promote / mention the program P1 _depends_ on
whether P1 itself references / recommends / promotes / mentions
nonfree programs in a significant way.

A few months ago I looked at contribution.html and pointed out a
paragraph about this.  I was sure it did not match the actual GNU
Project policy, but I couldn't make sense of what it did say.

I could not understand what condition it was trying to state.

Now I think I know what it was trying to say.  It was trying to state
a condition for accepting packages, something like, "As long as foo.el
offers to use at least one free alternative, it is ok, regardless of
what nonfree alternatives it may also offer."  The same thing you
were saying just now.

That crucially disagrees with the GNU Project's actual policy on
references to nonfree programs.  Our policy is stricter than that.
This misstatement needs to be clarified.

However, I found this in the CSS specification:
<https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/text-decoration-thickness>

The 'text-decoration-thickness' CSS property sets the stroke thickness
of the decoration line that is used on text in an element, such as a
line-through, underline, or overline.

/* Single keyword */
text-decoration-thickness: auto;
text-decoration-thickness: from-font;

/* length */
text-decoration-thickness: 0.1em;
text-decoration-thickness: 3px;

/* percentage */
text-decoration-thickness: 10%;

auto
     The browser chooses an appropriate width for the text decoration
     line.

from-font
     If the font file includes information about a preferred thickness,
     use that value. If the font file doesn't include this information,
     behave as if auto was set, with the browser choosing an
     appropriate thickness.

<length>
     Specifies the thickness of the text decoration line as a <length>,
     overriding the font file suggestion or the browser default.

<percentage>
     Specifies the thickness of the text decoration line as a
     <percentage> of 1em in the current font. A percentage inherits as
     a relative value, and so therefore scales with changes in the
     font. The browser must use a minimum of 1 device pixel. For a
     given application of this property, the thickness is constant
     across the whole box it is applied to, even if there are child
     elements with a different font size.

Scaling, as far as I have observed elsewhere applies to the entire
text, including decorations (this is the case in LibreOffice, for
example).

Subject: Getting rid of pathologically slow regexp matches
Message-ID: <jwv1pa9r14c.fsf-monnier+emacs@gnu.org>
In-Reply-To: 
References: 

Our regexp engine is using a backtracking approach, which has all kinds
of benefits but means that it does not enjoy the nice linear-time
complexity that theoretical CS says should apply to the problem of
regexp matching.

In practice this is usually not a problem: the time is almost always
linear anyway, and the backtracking approach has a fairly nice constant
factor, so all is well.  *Except* when it isn't: for those regexps that
can match the same string in many different ways (e.g. "a*a*a*" or
"(a*)*"), we hit the non-linear part of our algorithm which is typically
experienced by the end user as "Emacs froze" (because some font-lock
regexp bumped into a somewhat unusual line that hit that pathological
spot so the match takes minutes instead of a fraction of a second).

I have pushed to `scratch/regex-memoize` a patch which purports to fix
this problem by memoizing the failures during backtracking, so we get
back the linear-time complexity even for those nasty regexps.

I've been using a similar patch for a few years locally but it had
a fairly high cost in the "normal" case, so it seemed inappropriate for
`master`, but I have now refined the patch with enough "fastpath" that
the normal case is almost as fast as before in my tests:

I have found one test where I still see a 26% slowdown when running on
an ARM Cortex-A55 (a low-power in-order CPU), but in x86 CPUs the
slowdown is below 10% on all my tests (and for most tests there is
simply no measurable performance difference or a slight speed up,
except of course for those tests that bump into the pathological
behavior where the new code trounces the old one).

I'd be interested to hear feedback from people out there who may have
benchmarks of their own.  For the curious I attached the current patch.
