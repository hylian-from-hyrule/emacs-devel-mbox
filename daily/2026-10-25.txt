Subject: markdown-ts-mode: a plain-text base mode, with editing as a layer
Message-ID: <27357.63261.512714.425155@gargle.gargle.HOWL>
In-Reply-To: 
References: 

Good morning!

TL;DR: markdown-ts-mode's highlighting is great, but its editing layer
fights plain-text editing, which is the whole point of Markdown. I cut
it down to a highlighting-only mode in under 300 lines (link below), and
I'd like to propose a small base like that as the default .md mode, with
the editing machinery as an opt-in layer. Along the way I found a few
bugs (one runs arbitrary `*-mode' functions from fence names), a treesit
"fast mode" issue that needs a supported opt-out, a grammar bug, and
a case for generalizing mhtml's submode code instead of reimplementing
it.

----

I've been moving my setup to Emacs 31, and tried `markdown-ts-mode'. The
highlighting is very nice -- it follows the actual syntax, and code
fences in their own language are a real improvement. But the editing
layer got in my way almost everywhere. To actually use this thing, I'd
probably need to go over most key bindings, and disable/tweak many of
them. I think it's worth discussing now, while the mode is still
experimental and its design is open for 32.

The main point: Markdown was designed so that the plain text *is* the
format, and not needing any tooling is most of its appeal. Emacs is a
great text editor, and that's all a Markdown buffer needs, plus
highlighting. Typing a `*' on each side of a word is much easier for me
than remembering `C-c C-x C-f', and I don't think that's a fringe view.
With the default settings, I ran into some problems very quickly:

- RET in a table row is the same as <down>; at the last row it adds an
  empty row, which the next keystroke misaligns anyway.
- TAB in a table moves to the next cell after deleting the padding around
  all cells. Elsewhere (e.g., in a block quote), TAB is an outline-cycle
  command that does nothing visible.
- RET in a list continues the item, so starting a new bullet takes extra
  keys (delete spaces, add the bullet). I'm sure that there's some other
  key chord that I'll never remember that I should use -- but the
  default text editing is what I know in my bones.
- M-<left>/M-<right> are taken for changing levels -- if you have sexp
  navigation on these keys, you get unintended edits of text blocks, and
  therefore much frustration.

There's no way to get just "plain text editing + highlighting":
`markdown-ts-view-mode' is a read-only version of the full mode.

I'm aware that there are many people on the opposite side of this fence,
so I'm not trying to convert anyone. But given that what I need is
pretty much a strict subset of what's there, it seems like it would be
obvious to make a basic version that has no special editing
capabilities, and then another one that adds that on top of the basic
one.

Some size context: `markdown-ts-mode.el' is about 5,700 lines, plus
1,100 in `markdown-ts-mode-x.el'. Its .elc is the second largest of the
60 in lisp/textmodes (only bibtex is bigger), larger than tex-mode,
sgml-mode, rst, table, and artist. By the file's own sections, font-lock
and faces are about 350 lines; most of the rest is editing commands,
link handling, list, table and heading manipulation, filling, and the
code-block context machinery. Redundant code is a fact of life in any
software that serves more than one person, but it seems like a more
extreme case if there's a huge mode with well under 10% being the stuff
that I need...

To see what this base would look like, I made `md-ts-mode', a cut-down
version that is temporarily at

  https://gist.github.com/elibarzilay/7f4159764f28e28aa7ba95319fe67388

(it will move to a permanent place later). It is under 300 lines, uses
the same two grammars with the same pinned commits, derives from
`text-mode', and has no keymap and no commands. It was made as a quick
proof of concept, but turned out to be everything I actually need. It
has:

- full highlighting, with markup visible and full size,
- code fences highlighted in their own language (the language's mode is
  found through `auto-mode-alist', plus a small alias list),
- Outline and Imenu through the standard treesit settings, so plain
  `outline-minor-mode' just works,
- the real URL as `thing-at-point' (so `browse-url-at-point' works)
  anywhere on a link, including reference links and autolinks.

The trade-off I know of: fences are fontified by running the language's
mode on the block, so editing inside a huge fence re-highlights all of
it. Still, it's impressively small for a version that I think (a) is
very useful in itself as a basis for the full, um, "editor experience",
and (b) does everything needed for people like me, who have written text
with Emacs for a good number of decades, and are happy with it.

So I want to propose a small base mode like this as the default for .md
files, with the editing machinery as an autoloaded layer that people
turn on; or the other way around: have the default use this base with
the editing coming from a file with a way for me to turn it off. A small
base can settle (and stay stable) soon (most of the discussion so far
has been about editing features), and it's a better foundation for
different editing styles: e.g., an AUCTeX-like layer, an org-like one,
and whatever else people come up with -- all sharing one parser +
display setup. (And given how markdown became so important, more editing
styles are bound to sprout in the next few years.)

Working on a small mode also makes problems easier to see, when they
don't drown in a huge file of editing machinery. I ran into these in
markdown-ts-mode:

- A fence language runs any function named LANG-mode: a "column-number"
  fence turns on `column-number-mode', and "server" would call
  `server-mode'.
- Outline navigation sees only top-level (`#') headings: the outline
  predicate checks for a "section" node, but tree-sitter hands it nested
  sections under the grammar's internal name "_section2", so they fail.
  (md-ts-mode checks only the section's first child.)
- A big fence in an unknown language gets no highlighting, because of
  font-lock "fast mode" (below).

And some issues below the mode level:

- treesit's font-lock "fast mode" kicks in once a buffer has an expensive
  node, after which rules on nodes larger than ~6,000 chars never match --
  exactly big fenced blocks. There's no documented way to opt out;
  md-ts-mode sets the internal `treesit--font-lock-fast-mode' to nil. Modes
  that fontify embedded blocks need a supported way to do that.
- The markdown-inline grammar ignores the flanking rules for
  single-tilde strikethrough: in "foo ~bar ~baz ~blah" I get a strike
  through "baz ". This happens also with "*"s and "_"s. This is a bug in
  tree-sitter-markdown.

I'm not saying that these problems are unsolvable or hard -- they're
just very easy to lose track of when your code base is mostly not it.

Finally, one feature I deliberately left out: making keys in a fence
behave as in the fence's language. Done right, this needs swapping
keymaps *and* the buffer-local state (indentation, syntax table, comment
settings) as the cursor moves in and out. mhtml-mode does it for HTML,
markdown-ts-mode has its own ~250-line version, Org has its own for
source blocks, and in 31 php-ts-mode builds on mhtml-ts-mode to get it.
Rather than another private implementation, I think mhtml's code should
be generalized into a reusable library, with treesit answering "which
language is at point" -- and then Markdown would use it in a few lines.
Again, nothing blocking this from being done now, but it's that much
more difficult in a huge project.

I'll be happy to help with any of this if it makes sense. Otherwise, no
flaming intended: consider me happy with my quick hack and I'll shut up.
