First, yt-dlp only runs javascript if an optional dependency is
included. That optional dependency is currently "strongly
recommended", but is easily skipped. (I have been using yt-dlp and its
predecessors off and on for years without it every having the ability
to run javascript code).

filesystem or the network. (Basically, as a hashcash-style
anti-automation feature.)

>> I guess you are saying that `completion-ignore-case' is a user preference
>> _unless_ there is another user preference that would currently apply (such
>> as read-file-name-completion-ignore-case or tags-case-fold-search).
> No, I'm saying that there are two notions of case-insensitivity for completion:
> 
> - Are two choices that differ only in their case actually equal
>    according to the rules that apply to those choices (which means for
>    example that the exact casing used in the output of completion is only
>    a cosmetic detail).
>    E.g. completion of a Common Lisp identifier (case-insensitive) vs
>    completion of an ELisp identifier (case-sensitive).
>    This is not a user-preference but reflects the actual semantics of the
>    strings we're completing.

Thanks! Trying to wrap my head around it properly now.

> - Do the users want to be able to find also those completions that have
>    a different case than what they typed.  In this case, the casing used
>    in the output is not just cosmetic.
>    This is a user-preference.  The user's preference may vary from one
>    completion to another, tho currently we don't support `ignore-case`
>    in `completion-category-overrides` (although we do have
>    `read-file-name-completion-ignore-case`).

If these are two different purposes, do we make provision for differing 
values? E.g. if Elisp identifier is case-sensitive but the global user 
preference is "case insensitive" - e.g. the user would like to see 
completions in any case for their lowercase input.

(It doesn't make sense in the opposite direction, I suppose.)

Or do we only obey the user preference if the completion table does not 
express a preference of its own?

That is a dogmatic simplification, and it leaves many points
unspecified.  It does not directly imply conclusions about some
crucial questions.

If we are to have something in Emacs that directs people to a Hermes
site H1, we need to ask what other sites or software H1 suggests using
along with Hermes.  To say only that H1 is "user-configured" leaves
crucial points unclear -- it is not enough basis to judge whether H1
is acceptable by our standards.

Here are three things "user-configured" could mean for H1:

* H1 invites the user to configure it by choosing from various menus,
and we have verified that each entry in each of those menus is
freedom-respecting.

In that case, linking to H1 is ok.

* H1 invites the user to configure it by choosing from various menus,
and some of the choices in those menus are ethically unacceptable by
our standards.

In that case, we should not link to H1.

* H1 invites the user to configure it by typing in the names of
various programs to use to do various subtasks.  H1 itself doesn't have
lists of the programs you could use; you have to find that somewhere
else.

In that case, it is ok to link to H1, but we should also present lists
of names of freedom-upholding options that we recommend to users for
these subtasks.

lists, so we need to make sure that it leads the user to lists which
are vetted _our way_ for freedom.  At least, that _our_ version of
Hermes, the one we link to, does so.

I have not looked at where it would be most natural to implement it, no,
only at where it would make sense to store the user's preference.  🙂

As for how to combine the completion-table's choice of case-ignore and
the user's stated preference, that's also a good question.  I think
the current code uses approximately the following convention:
we presume that things are case-sensitive by default, then the outer
code (presumably representing the user's preference) sets or binds
`completion-ignore-case` if we want to ignore case, and lower down in
the completion-tables, we leave `completion-ignore-case` untouched (and
obey it implicitly) where the table is supposed to be case-sensitive
and we let-bind it to t when the table is supposed to be
case-insensitive.

That can break down occasionally when some piece of completion-table
code feels the need to let-bind `completion-ignore-case` to nil, but
AFAIK this is quite rare.
