Dear Eli,

You ask that I not be CC'd because I am "not an Emacs maintainer" and 
therefore "cannot possibly have any constructive or useful contribution" 
to a discussion about Emacs packages. I would like to address this 
directly.

I am a subscriber to emacs-devel.

I signed up to this list. I participate in discussions about Emacs. The 
question of which packages Emacs distributes, and what those packages 
lead users toward, is an Emacs question. It is not a private matter for 
maintainers only. I am free software advocate just like you.

  am a GNU user, and the policy at stake is GNU's policy.

The question is not whether I have commit access. The question is 
whether the packages Emacs distributes are consistent with the GNU 
philosophy that Emacs exists to serve. Stallman has said they are not, 
in the case of hermes.el. I have provided evidence and cited policy. 
That is a contribution, whether or not I hold a maintainer title.

Personally, I hate to have in GNU and Non GNU those packages that steer 
users to SaaSS:

- hermes.el (NonGNU ELPA) — Package description links directly to the 
Hermes Agent quickstart page, which presents "Easiest path: Nous Portal" 
and "the recommended fast path" — a SaaSS service. The dependency 
(Hermes Agent) steers users to SaaSS through its installer.
- codex-ide (NonGNU ELPA) — Directly depends on the Codex CLI, which 
defaults to OpenAI's proprietary SaaSS service. Its package description 
promotes this dependency without warning.
- minuet (GNU ELPA) — Package description directly promotes SaaSS. It 
lists OpenAI, Claude, Gemini, Codestral, and DeepSeek as providers with 
SaaSS endpoints as defaults.
- gptel (NonGNU ELPA) — Package description begins "Interact with 
ChatGPT or other LLMs," pointing users first to a proprietary SaaSS 
service.
- aidermacs (NonGNU ELPA) — Front end for Aider, designed around 
connecting to remote LLM APIs rather than local models.
- ellama (GNU ELPA) — Supports multiple providers including proprietary 
SaaSS ones.

The "not a maintainer" argument has been used to dismiss every critic in 
this thread.

- Arne Babenhauserheide was told he "knows nothing about what we do" 
because he is not a maintainer.
- I am told I "cannot possibly have any constructive or useful 
contribution" because I am not a maintainer.
- Stallman himself — the founder of GNU — is told his conclusion is 
wrong because he "disagrees with our judgment."

If the only people permitted to speak are those who already agree with 
the maintainers, then the discussion is not a discussion. It is a 
ratification.

I have raised concerns about hermes.el, codex-ide, minuet, gptel, 
aidermacs, and ellama — not one package, but a category. The pattern is 
that GNU ELPA and NonGNU ELPA are accepting packages that steer users 
toward SaaSS. That is a structural question, and it deserves structural 
attention, not dismissal by title.

-- 
Jean Louis

Richard Stallman <rms@gnu.org> writes:

> The concept of SaaSS does not apply to Mastodon servers
> because the job they do is communication between users.

You’re right: Mastodon wasn’t the best example here.

> SaaSS (for the individual user) means using someone else's server to
> do a computing task that is solely and and totally your own, so there
> is no inherent need for anyone else's computer to be involved at all.
> To use someone else's server for your personal activities gives that
> someone power over them, power which only you ought to have.

To me that depends on whose computer I use. As long as I could run the
same program locally, I don’t mind running it in places I trust. Those
places could be friends, a community I’m part of, or people whom I
contract for that service.

If I don’t need some hardware all the time, it can be a good idea to
share it with others.

If I could compile my code on my own system, but I could compile it much
faster by running parts of the compile on the computers of my friends,
too, then I don’t see a problem with that.

In short: „it’s OK to rely on others, as long as I can step out“.

That is a slippery slope, though, because I may not be able to work
efficiently without other computers anymore, and then I would grant
others power over me. That’s why I prefer running stuff locally.

For example distcc is OK for me.

But it would be better if distcc were licensed under the AGPL instead of
the GPL, so people couldn’t run unshared patches that I cannot get but
may start to depend on. AGPL would reduce the risk of slipping into such
dependency.

I think the comment should explain *why* this call is non-essential.
And I suspect it's not really the right place: e.g. it will cause Tramp
to "not do" the requested operation in some cases (e.g. because it
would require prompting for a password) but that in turns means that
`vc-dir--count-outgoing` will return the wrong information.

I think the general idea is right, but maybe not the place: maybe the
reason this is non-essential applies not just to this call to
`vc-incoming-outgoing-internal` but to the call to
`vc-dir--count-outgoing` itself.  So maybe we should move the binding
higher up (or even to the caller) and add a comment saying that the
outgoing count is non-essential in the sense that it is not important
enough to justify pestering the user for a password.

Thanks, Eli.  I appreciate you trying to resolve this.

The patch assumes that Hermes Agent runs on the same machine as Emacs.
That's not necessarily the case.  Users can run the agent on a powerful
desktop and connect from a laptop.  hermes.el supports simultaneous
connections to multiple remote hermes instances.  Writing a config on
the laptop would not configure any of those.

Even locally, putting a model name in a config does not install it or
start the server needed to use it.  Hermes Agent connects to a model
provider, local or remote.  It is that provider, such as a local Ollama
or llama.cpp server, that runs the model.  The default model setting
just tells Hermes what to ask the provider for.

For a local setup, hermes.el talks to Hermes Agent, which talks to an
inference server.  That server loads the model weights and tokenizer
and runs the model on the CPU or GPU.  It needs enough RAM/VRAM and, for
GPU use, compatible drivers and runtime support.  Installing and serving
the LLM is the provider's job; the agent uses it to carry out tasks.
Tools (e.g web tools) have their own backends as well.

These requirements go beyond the agent harness, let alone its Emacs
interface.  Choosing an acceptable model name does not supply that
model, its server, or the rest of this setup.  I don't think making an
Emacs frontend responsible for that whole environment is reasonable,
and writing a default config would not solve it.

to a new user, steers them toward SaaSS. I do not see any "free
SaaSS": whether the server software is free is beside the point,
because the service still performs the computing on the user's data
and the user still loses control of it. That is what the policy
addresses.

> This means we can get rid of the problematic part.

hermes.el can be changed — it is in the maintainers' hands. Hermes
Agent cannot easily be changed: it is the dependency, and its
installer, its documentation, and its provider list are built around a
SaaSS offering. The package description in ELPA points to the Hermes
quickstart page, and that page says, in the Hermes project's own
words, "Easiest path: Nous Portal" and "the recommended fast path."
That is the steering.

> If I understand hermes agent correctly, then all that's needed on top 
> of
> this patch to avoid steering new hermes users to proprietary SaaSS is
> to add a config string that sets the model and provider to a non-empty
> string that refers to something that's acceptable by GNU principles.

If that is what is needed, then the fix is straightforward, and the
question is why it has not been made. Until it is made, the package
continues to do what it does — depend on a tool that recommends SaaSS
— and the policy continues to apply.

> As an aside: hermes.el is huge and has a ton of functionality. Blocking
> it from elpa because we don't want to apply this 15 line change in
> hermes.el to prevent the problematic part of the hermes agent from
> running on first start would feel like a waste.

Size and quality are not in question. What is in question is whether
the package steers users to SaaSS. A large, well-written package that
does so is not made acceptable by being large and well written. The
same applies to other packages in the archives: minuet's default
provider is DeepSeek's cloud API, and the package description
advertises it as such.

For users who want to avoid packages that steer to SaaSS, the setting is 
simple:

(setq package-hidden-regexps
       '("^hermes$" "^codex-ide$" "^minuet$"
         "^gptel$" "^aidermacs$" "^ellama$"))

That is a user-side workaround, not a policy solution. The policy
question is for the project, and it is still open.

Hello,

I've been following discussions about how to treat packages that 
integrate emacs with LLMs, and I would like to make a pragmatic point 
that I think has been missing so far. I do not wish to add more noise, 
so feel free to to shut me up :)

I'm not very good at writing this kind of prose also.

In my experience, Emacs is one the best possible environments for 
interacting with LLMS, even with all the spectacular artifacts that the 
proprietary clients have. Prompts are written in emacs, with the editing 
power that it implies. The output can be given in Org mode, so it 
becomes a powerfull structured document that I can later edit, link, 
export and keep rather than a "transcript" inside someone else´s interface.

I should be clear what emacs competes with now. VS Code with copilot, 
and editors built from the ground up for this. Users are going there, 
precisely because of that integration. More and more professional 
programmers are required by their employers to use such tools, on the 
grounds of productivity (maybe misguidedly). Non programmer users rely 
on the product's own tools. Academic and research users would be much 
better served with Emacs.

I would also question the framing as a SaaSS. It is "Hardware as a 
service" as much as it. That is closer to renting computing
power than to a service that substitutes for a program the user
should be running themselves.  The client that talks to that
hardware, however, can and should be free, and Emacs is or could ve an 
excellent one. There is not free alternative. And people need the LLMs 
to be competitive in their work, or at least they think they do.

LLLs are a reality, and are also a technical wonder. Reducing emacs' 
support for them as "promoting non-free SaaS" is in my opinion 
self-defeating for GNU and for emacs' user present and future. I think the
real question is whether people use a free program to interact with the 
LLMs or something else. Keeping users inside Emacs keeps them closer to 
free software, not further from it.

To give a personal example of what a free program gives its users:
my LLM subscription doesn't include API access, only the vendor's
own command-line agent.  No Emacs package supported that setup, so I
wrote a wrapper around the command-line tool myself.  It gives me
Copilot-style inline completions and a chat interface inside Emacs.
The vendor never intended that, and no proprietary editor would have
let me do it on my own terms.  Emacs did, because it is free and
extensible all the way down.  That is exactly the kind of thing we
risk losing if LLM support is treated as something to keep away from
Emacs.

Cecilio Pardo
