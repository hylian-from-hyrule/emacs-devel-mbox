>> For example, should we consider using a &key argument?  Perhaps not

Can't say I love the long arglist either (and it wasn't my original plan
to extend it), but I'm also in no hurry to change the function's calling
convention (it has a whopping 25% fewer parameters than completing-read!).

OTOH, the current refactor should make it slightly less painful to add
keyword arguments given sufficient demand.

>> I'd also like to hear the motivating use cases for sorting where it's
>> important to be able to pass a parameter, instead of just calling sort
>> on the resulting list.  The latter would avoid us adding yet another
>> optional argument.

Sorting the final list is not equivalent to sorting each individual
subdir, at least not without relatively expensive post-processing.

The whole bug report was due to the old code sorting a little too
coarsely: it didn't strip trailing directory separators, so could place
"foo-bar/" before "foo/" where "foo" would otherwise precede "foo-bar".

Adding a means to control this (as a compatibility escape hatch and/or
as a new feature) seemed like only a small compromise / price to pay.
