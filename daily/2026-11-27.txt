Yep yep, (xref--get-history) should correctly delegate there.

Right now my plan is to add a manner of invocation that will mean "use 
location from before the latest jump". So that location will only be 
"kept" while you keep using that invocation (e.g. 'C-u C-u') or if the 
regular jump continues to be with the same backend.

Using the same concept, I'm considering other UI approaches. E.g. prefix 
command (but it'll either need a binding or expect the user to M-x type 
it in full). A minor mode was discussed as an option, but a binary 
yes-or-no doesn't seem very suitable for this kind of feature (it would 
be easy to do, though).

Opinions welcome.

Eli's suggestion is implemented in the patch I already sent, but that's 
rather limited in scope.

> I suppose this would help to solve the real problem that I experience.
> Sometimes in another working tree (for example, in a branch)
> in a ELisp file 'M-.' needs to jump to the original tree
> where Emacs was started.  But sometimes 'M-.' needs to jump
> to the file in the branch tree.  For the former need to use
> 'elisp' backend, for the latter 'etags' backend.  So would be nice
> to have a way to select the backend and keep it for navigation.

Hmm, I'm not sure how to conceptualize this kind of feature. Choosing 
just a backend seems insufficient, like described earlier.

We could have a prompt to choose an earlier location as a location to 
jump from, though. Maybe grouped by backend, but I'm not sure about that 
- after all you might as well have two different worktrees using the 
same backend (e.g. Eglot) and you might still want to be able to choose 
between them.

Maybe a command that sets an "origin location" (with completion) for all 
subsequent jumps is the way to go. And a command that resets it.

Or a command that affects just the next jump. Though this would probably 
be easier to apply with 'C-u C-u', as discussed before.

As for implementation strategy, I'm thinking of a new backend type that 
could be returned by xref-find-backend and wraps a tuple 
backend/buffer/position retrieved from history (or just buffer/position, 
since backend is recoverable).

This is an issue we must properly address.  It sounds like they didn't try.

Linux adheres to the open source philosophy.  If Linux development
became totally dependent on a nonfree tool, they might not see a
problem in that.  We, in contrast, _must_ make sure that does not
happen.

This is an additional reason to put explicit limits on our usage of
LLMs.  It does not imply _never_ using them.  But we should _never_
steer anyone towards a nonfree or SaaSS LLM.

Another issue is that we must take care not to be locked into one
particular LLM, either in general or in working on one piece of code.
Those who do use LLMs should switch around, to make sure of this.

We should also make sure that LLMs don't pressure us into using
certain kinds of designs and not others.

All this is supposing that the copyright issues have been resolved.

maintainers watch the installed changes and raise any issues they see
post-factum.

So "trusting LLM-generated changes" is not on the table, and shouldn't
be, IMO.  Every such change should be reviewed as we do with any other
changes, probably even more thoroughly.  And I don't see why we would
be "likely to feel pressure" in these matters, more than we do now
with changes produced by humans.  If anything, I think any pressure to
accept changes, if it exists, is _greater_ when talking to a person
than when it's machine-generated, because we know a person has
feelings that we don't want to hurt, to avoid the risk of losing a
potential contributor and possibly a future member of the development
team.

> If the change is easy to understand, it may do no harm (in terms of
> design) to accept it.  But if it is hard to understand, we should
> decline it.

We don't accept changes that are not understandable, full stop.  Once
again, this is a non-issue.

> We can help ourselves stay ready to say no if we practice the will
> power to say no.

We said NO already quite a few times, so I see no problem with us
being ready for doing that in the future.
