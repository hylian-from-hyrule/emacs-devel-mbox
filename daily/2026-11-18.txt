Also, since we are having this discussion, another quirk from the past
is that a non-ASCII query string is sent out verbatim, e.g.

288 UID SEARCH TEXT "äößü"

when neither LITERAL+ nor UTF8-NATIVE is available. (!) I did not change
this behavior, even through it's practically guaranteed to fail. That's
also why Gmail search broke down after Google stopped offering LITERAL+,
allegedly for security reasons.

Yet another quirk is a lack of consistency between the way double quotes
are treated. When the string is sent as a binary literal, the IMAP
server seems to treat the quotes as part of the string, but not if the
same string is sent in quotes as in the example above. It's, obviously,
up to the client to reconcile the two.

All in all, we will never get tired going down this IMAP rabbit hole.

  > > Please explain, because I see no contradiction here.  You can make

  > > if you do the latter, but that doesn't mean the former isn't possible?

(Someone mentioned a program called Nuspell, but I don't know
what that is or how it relates.  As far as I recall, vibe-spell is
an LLM translation of Hunspell.)

If it is clearly tempting to use an LLM to port changes in Hunspell
into vibe-spell, we cannot sensibly treat vibe-spell as independent
source code.  We would betray our goal if we installed code whose
maintenance depends on a nonfree program or SaaSS server.

That would also add to the general pressure to yield to LLMs.  We will
certainly face such general pressure, as people who don't feel concern
about this issue try to insist we become dependent on LLMs.  We will
face a struggle to refuse.  It would be foolish to choose to make that
struggle harder.

I am convinced that one requirement for including LLM-generated
material in GNU Programs must be that the LLM-generated material be
completely divorced from the LLM that generated it.  In other words,
we must insist there be no reason to anticipate pressure to use LLMs
to update it.  It must be source code, pure and simple, to be
maintained like the rest of Emacs.

In particular, LLM output should not be a machine translation of a

The '+++' typically marks the "new" file name, the "---" the "old",
corresponding to the line prefixes further down -- space meaning
no change (those are so-called "context lines", to help ensuring
that one is looking at the right thing) "-" means "delete this line"
(or "old"), "+" meaning "add". Then there are those "@@...@" to
denotate where in the file the action is. See, for example

  https://en.wikipedia.org/wiki/Diff#Unified_format

The whole thing is called "unified diff format", and you get that
with

  diff -u <oldfile> <newfile>

(or just with "git diff").
