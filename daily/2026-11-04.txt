Eli Zaretskii <eliz@gnu.org> writes:
> Please at least wait until there's some sign of something like that
> happening in Emacs.

How the discussions went about whether packages that steer people into /
suggest using / (insert other wording) proprietary services was such a
sign for me.

> And I'm most alarmed by the suggestion that we should reject someone's
> code based on something that is unrelated to the code itself.  

There is a difference in code: people who hand out LLM output do not
actually write the same code as those who don’t, even when they work on
the same codebase, because code that works well for LLMs is different
from code that works well for humans.

To me that does not feel like working on code together, but more like
someone submitting code generated from UML diagrams and developed via
these – with comments that ease detangling, but without actually
including the original source (the diagrams).

And expecting others to read the generated code, but as reply to reviews
adjusting the UML diagrams and regenerating the code.
And it’s exhausting to ask them for readability improvements (just to
see them ignored the next time again, because they don’t read the code).


At that point (with code generated from UML) I’d see three main options:

- commit the original source (the diagrams) and accept that parts of the
  projects require understanding one more language to contribute. The
  source is then no longer the source of truth.

- accept that the original source is not included and decide what to do
  with the detangling comments (others can’t maintain them reliably).

- reject the contribution.


But the first isn’t actually possible with LLM output, because prompts
and plans don’t work the same in different models or even versions of
the same models, and they aren’t meant for humans (else they wouldn’t
contain the phrases needed only by the LLM) and also not for being run
multiple times.

When collaborating with LLM-users at work I’ve already had to maintain
other people’s AGENTS.md file and I’ve been directed to read long-winded
architecture files that are a kind of code but not really and require
knowledge of what the LLM of the current quarter makes of them to
understand what they mean.

And even more than with UML generated code, there’s a power disbalance:
they expect me to read their generated code to work on the project, but
they only see my code through the lens of their LLM.
Not like auto-complete with a rendered docstring, but rather like asking
“what does this file do?”.

How deep that goes differs by person: I’ve seen a continuum between
caring for the code itself and not reading any code, but there are only
two people of whom I know that they started using LLMs and still managed
not to move towards not caring how the actual code reads for humans.

The extreme end is that someone tells you that their code (they don’t
understand) is better than yours because they have 10 times as many
tests (they didn’t read).
And expecting you to replace your code with theirs due to that or to
explain why you don’t after being the first who read it – and then to
argue with them because they trust the LLM more than you.

Therefore I think that opening the door to LLM-generated code only a
little bit is a path that leads to non-LLM users being pushed out of the
project.

> Because the next thing we will be requested is to reject code
> of people with particular views or opinions, or people living under
> certain regimes, etc. etc.  We never did anything like that, and
> IMNSHO we shouldn't, ever.

I intended not to write in this thread again, but I very much agree with
this point.

That’s why I decided to explain why I think that it does not apply to
contributing LLM output.

And I’m sorry that I couldn’t make that shorter.

>> The point is that producing LLM output uses a different language than
>> writing code. So it effectively adds a language to the project.
>
> You will need to explain that, because I really don't understand what

> language, be it C or Lisp, in which Emacs is written.

That’s what I tried to do with the UML analogy: when you generate code
from an UML diagram, you do not actually write in the language of the
code. You write UML.

Similarly when you write prompts, you do not actually write the code,
but you write instructions that say something about the code, but to get
them right, you have to have a feeling for the representation the LLM
has of the code (which you can’t actually know).

Depending on the usage style, this can be closer to or further away from
the actual code, but in any way it’s not actually the code. And it’s
very different from refactoring tools with which you do precise
manipulations of the code on the level of the code.

An easier to convey example is with AI-art: if you tell an AI model
“make this blue”, it often doesn’t only make this blue, but adds other
changes. An art director explained a while back that this makes it
almost impossible for him to work with people who use those tools. While
the results seem similar, they don’t actually use the same language to
produce them.

And that creates a constant pressure to just accept what the model
outputs today (besides anchoring effects that make this stronger),
detaching the user from the actual code. Example quote (I heard multiple
times): “not exactly what I wanted, but doesn’t do harm, right?”.

It also causes pressure to look more at things the tool can check (e.g.
“the tests are green” or “I can click through”) and less on the code.
But those are indicators that help catch common errors and not the
source of truth for correctness (except for programs like sqlite that
have massive testsuites and are exposed to every strange bug under the
sun).

>> Not just some language (which would already be risky), but a language
>> that does not have a corresponding source that can reproduce its output

> Once again, what needs to be documented and recorded as part of
> admitting such contributions is a separate issue.

It’s not about what to admit: it’s about whether it would actually be
possible to just say the equivalent of “let the source of this part be
the UML diagram / XML definition / …”.

On 2026-11-04 10:08, Gerd Möllmann wrote:

> ...and the difficulty that LLM output is non-determinitic

 From view point of running local the local LLM inference, the above 
statement is only true when user sets the temperature to something else 
then zero. In GNU project we should never discuss running the remote 
SaaSS API but local computing.

If temperature is zero, the output is deterministic and reproducible. Of 
course other parameters should be made known as well to get full 
reproducibility.

Example:

llama-cli --temp 0 -m 
/mnt/nvme0n1/LLM/quantized/Qwen3.5-9B-Uncensored-HauhauCS-Aggressive-Q4_K_M.gguf 
--prompt "Who is RMS aka Stallman?"

Try it out. It gives deterministic output each single time. The above 
prompt will always give totally same output, as the model picks the 
single most probable token at every step.

It is reproducible. It is alright to use temperature zero in coding, 
especially in debugging and testing, it is even faster slightly.

In an LLM-allowed programming environment, programmers could use a 
shared model (with same checksum) to collaborate deterministically, 
generating Emacs lisp functions sequentially while maintaining full 
understanding of each function and ensuring a coherent workflow.

Thus, the problems with foundation of not being deterministic can be 
resolved by establishing a deterministic, local inference workflow using 
a shared same model with a fixed checksum.

> Our job is to make sure that code that lands in Emacs is useful,

There's one issue with that - after such code gets merged, it can
become your business.

Say, someone made a contribution to Emacs, a particularly large one.
They spent tons of tokens on it, made tests and all, and the code
looks solid.  Maintainers do the review, ask for some changes.  The
user spends more tokens, changes the code, and eventually it is
decided that all is good and the code is fine to merge to Emacs.

That person doesn't understand the code they made, because it was done
by an LLM.  Sure it's their problem.  But once it gets merged, it is
now problem for the maintainers.  The contributor walks away, and if
in the future any issues arise, that person may just not respond at
all.  Now someone else needs to go through all that code and figure
out the intentions that the LLM had while writing it.  This can get
out of hand pretty fast.

I sometimes submit bugs to Emacs, and I often see that someone who's
responsible to the changes that introduced these bugs are called, and
they come and fix these bugs, as any responsible contributor should.
Assuming that this will work the same with people who used an LLM to
make a contribution is problematic, and I've already encountered it in
the projects I maintain.

Sure, this can happen without LLMs involved - there are irresponsible
people who would walk away just the same.  But allowing the use of LLM
opens the door to getting much more of such contributions, and can quickly
overwhelm a small team with amounts of code they now need to maintain
without help.
