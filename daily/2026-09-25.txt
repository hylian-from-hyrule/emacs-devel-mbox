You could set `debug-on-error' and also `debugger' to something
different than `#'debug'', e.g., to something like

  (lambda (&rest args)
    (message "--- DEBUG: %S" args)
    (backtrace)
    (message "--- END DEBUG"))

so that entering the debugger just means printing the error information
and its backtrace rather than being put into the interactive debugger
and thus stopping the world.

  > >> If you do look if dependency is non-free software, by that analogy you
  > >> are looking at dependency, call it second leg
  > > 
  > > No, the second leg is not our responsibility.  And neither are the

  > If second leg is not for maintainer to think about, than it contradicts 
  > to the rule that ELPA package should not depend on non-free software.

It depends on how strongly related the first-level referenced program
or server is to the ones it references (the second level).

If they are mere suggestions on the side, we need not worry about them.

But if using the first often calls for using the others, that is a
dependency or nearly so.  In that case, our directing users to the
first one implicitly directs them to the others too.

If the first program or server asks the user to choose from a list of
others to use, that has the effect of recommending each alternative in
that list.

How the Hermes site relates to various other servers and programs --
and our judgments of those -- is one of the major questions we should
have examined in a careful consideration of hermes.el.  The
discussion, such as it was, did not go that far.  The way we handled
the question of adding Hermes to ELPA was not careful enough.

This is not the only time such a problem has occurred, and that is why
I have concluded that we need a new system for evaluating packages for
ELPA (both GNU ELPA and NonGNU ELPA).

The system needs to be designed to lead us to probe what components
(programs and servers) are implied by the proposed package.  In
complex situations, that may take substantial time.  But that delay is
worth while if it avoids making wrong decisions.

That means the system needs to be designed to avoid rushing to a
decision (which might imply skipping some of the necessary probing).

One idea for how to do this is to have a specific list of package
evaluators, and continuing the evaluation of a package until all
of them agree it has covered all the crucial points.

The concept of SaaSS does not apply to Mastodon servers
because the job they do is communication between users.

SaaSS (for the individual user) means using someone else's server to
do a computing task that is solely and and totally your own, so there
is no inherent need for anyone else's computer to be involved at all.

someone power over them, power which only you ought to have.

By contrast, communication between users on the internet needs to
involve internet infrastructure one way or another.  In other words,
to involve computers that are not controlled by either of those users.
So it would be absurd to condemn using those intermediary computers
_for communication_.

You and I are using very different understandings of "steering" users.

When an activity (a program or site) proposes specific alternatives
(programs or pages) to the user, that steers the user towards the
specific alternatives mentioned.  Another way of saying this is that
it recommends those specific alternatives.  The point is that the idea
of using those alternatives is part of the influence of the activity
on the user.  Depending on what specific alternatives the site
recommends, it may (or may not) be directing the user into
giving up freedom.

The other possibility is that the activity asks the user which program
or page to use.  That doesn't influence the user towards or away from
any particular alternative.  Whatever the user chooses, the activity
is not to blame.

Some recommendations are pushier than others.  If the activity
mentions a nonfree program in passing, that may not be very
influential.  Maybe we should overlook it.  If it mentions Windows,
Android or MacOS, there's no point in making a fuss, since users
already consider using them.

By contrast, saying "Now choose one of these options" is a very loud
kind of recommendation -- the user can't ignore it.  We should not
ignore it when we judge the activity.
