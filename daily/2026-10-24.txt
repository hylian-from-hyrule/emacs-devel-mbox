On Friday, October 23rd, 2026 at 12:11 PM, Stéphane Marks <shipmints@gmail.com> wrote:

> Aha, I see now. I have to admit it's not something that appeals to me as I prefer using approaches like Makefiles and consider them source code. A quick scan suggests that it is tough to share a single xc file across "environments"; i.e., to easily override environment variables to run in production vs. development.

Right, xc not as powerful as make, and in many cases make is the better choice. The aim of xc is to ensure the project's top-level task entry points are well documented in the README and easy to run.  For example, autotools projects that have README instructions to run "configure, make, make install" could use xc to ensure that those exact instructions produce the desired result, and set up a system to alert them to any README breakage.

Here's an example of one of my projects where I use xc for my dev workflow and also for automatic continuous integration. You can see I have a step for CI that just sets some env variables & runs xc again: https://codeberg.org/ryanprior/fennel-packer#headline-23

If things got much more complicated, I would turn to make or bash or similar in service of keeping the README easy to follow. I do like how easy it makes it to hyperlink specific automation steps, and I like that my green "build | success" badge in the repo will turn red if my README is incorrect.

I wrote a high level blog post laying out my motivation for xc in case that's interesting: https://www.ryanprior.com/posts/put-your-runbook-in-your-readme/

Happy hacking,
Ryan

practice. There is no reliable way to determine whether a package was
developed with AI assistance simply by examining its source code or commit
history.

developed using AI tools, but their commit histories simply don't
acknowledge that involvement.

developers who are transparent about their use of AI, while allowing those
who don't disclose it to go unnoticed?

and whether the maintainer understands it and takes responsibility for it,
rather than whether AI was involved in its development.

The current policy of not accepting LLM-generated code is because the
copyright and licensing of such code is uncertain.  One possibility is
that the authors of code which was used in the LLM's training set
could sue the FSF and the GNU Project for using their code in Emacs,
and we want to avoid this danger, if it's real.  The FSF lawyers are
currently considering this and other legal implications of using
LLM-generated code in GNU projects, and once they produce their
advice, the policy will be amended accordingly.
