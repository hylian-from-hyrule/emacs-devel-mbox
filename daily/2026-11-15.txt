>   d:\gnu\git\emacs\feature2\src/igc.c:6371:(.text+0x7a62): undefined reference to `sigdelset'
>   collect2.exe: error: ld returned 1 exit status
>   Makefile:716: recipe for target `temacs.exe' failed
>
> I fixed the error so that Emacs at least could be built, but I'm not
> sure whether it's correct, because I don't think I understand the
> strategy.  Can you explain the purpose of calling sigaction for
> SIGSEGV in igc_defer_sigprof?

sigaction is called two times: the first call reads the current value;
the second call sets the value with a modified sa_mask.

> In particular, is this at all needed on
> MS-Windows, and if so, why?

Probably not.  The problem on GNU/Linux, is that we can have a sequence
like:

  1. SIGSEGV caused by some ordinary code executes MPS's fault handler
  2. SIGPROF, caused by the profiler, interrupts the MPS fault handler
  3. handle_profiler_signal causes another SIGSEGV in trace_hash

at this point Linux terminates the process, because usually receiving a
SIGSEGV is not allowed while executing a handler for SIGSEGV.  (It could
be allowed by setting the SA_NODEFER flag, but MPS doesn't set that.)

I don't know what MS-Windows does in the analog situation; maybe it
allows nested SIGSEGVs by default.

Anyway, I think I found a another way to avoid step 3 so that
igc_defer_sigprof is no longer needed.

The origin was this proposed module vibe-spell that was generated by 
running the source code of a library through an LLM to produce ELisp code.

One of the valid issues is that spelling tools based on ispell as 
suboptimal and alternatives like jinx - of which I'm a happy user- are 
sometimes difficult to spin up, because they depend on a C module that 
may be non-trivial to generate on some systems.

I was pointing out that the alternative was to write an external utility 
similar to a language server that you could interface with using a 
JSONRPC interface and implement the queries in an equivalent way to how 
eglot interacts with the language server.

This would isolate Emacs from the library's evolution as opposed to 
having to run newly released versions of the original library through 
the LLM to keep up with changes in that codebase.

To make my point, I added a simple toy implementation of the server part 
with a shell script to demonstrate how it would work.

At that point, the idea of a foreign function interface (FFI) as part of 
core Emacs to face this kind of situations was brought up.

Guys, all this talk about adding FFI to Emacs is pointless, because it

too easily with non-free libraries, which we want to prevent.  We
developed the module subsystem as an alternative, which requires the
author to declare GPL compliance, as a precondition for loading the
module.
