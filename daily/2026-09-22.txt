On 18/09/2026 17:27, Stefan Monnier via Emacs development discussions. 
wrote:
> As for how to combine the completion-table's choice of case-ignore and
> the user's stated preference, that's also a good question.  I think
> the current code uses approximately the following convention:
> we presume that things are case-sensitive by default, then the outer
> code (presumably representing the user's preference) sets or binds
> `completion-ignore-case` if we want to ignore case, and lower down in
> the completion-tables, we leave `completion-ignore-case` untouched (and
> obey it implicitly) where the table is supposed to be case-sensitive
> and we let-bind it to t when the table is supposed to be
> case-insensitive.

Following that description, it seems the use of 
xref-backend-identifier-completion-ignore-case in xref-read-identifier 
does TRT actually?

It reflects the user's preference if as you say it's what 
find-tag--completion-ignore-case returns, because 
xref-backend-identifier-completion-ignore-case<etags> calls just that.

And xref-read-identifier binds completion-ignore-case to its result. The 
method also defaults to just 'completion-ignore-case', for backends that 
do not embed the user's preference (e.g. some user option).

It diverges with your description in tags-completion-at-point-function 
which also binds completion-ignore-case (while you describe how it 
should be left alone), but since it becomes just a second nested binding 
with the same value, it shouldn't make anything worse.

If we wanted to transition to the scheme using category-overrides, we 
would apparently have to create a separate category for `xref-etags' 
completions. And for it to honor the semantics of tags-case-fold-search 
(which defaults to the value of case-fold-search), the categories' item 
will need to support a functional value. Which is fine, but would make 
it a non-transparent value as well.

Provided there is a case of users wanting to tweak these more directly, 
we could go in this direction though.

  > Expecting an Emacs interface to set up a fully free environment for

That statement is true.  GNU Emacs is not in charge of configuring
the whole system on your machine, because it is not the whole GNU system.

But _to the extent that_ Emacs guides in some cases the choice of
other programs to install or use, or network sites to use, it should
lead the user only towards freedom-respecting choices.

The words "lead the user towards" are chosen with care.  Nothing in
the GNU system is supposed to block the user from intentionally
installing a nonfree program, or intentionally communicating with a
web site that sends nonfree programs to run in per computer, or
outsourcing computing to a server someone else controls, though it
might ask, "Are you sure you want to install that nonfree program?" or

    non-free software (in addition to perform whatever services
    'foobar' needs), still others perhaps use SaaSS.  However, users
    can configure or invoke 'foobar' so as to avoid those non-free
    sites

This is exactly the situation with hermes.el.

verify that none of them can ever "lead the user" to anything unjust?

only practical result of such a request will be that no package will
