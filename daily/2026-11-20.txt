Sorry for the trouble. The cause is on my side: `#+BEGIN_HTML' has not
been an export block since Org 8.0. Current Org reads it as a special
block named "HTML", so its contents are parsed as Org text, which gives
the escaped tags and the bare image URLs turned into <img> that you saw.

> Github happily displays this Org's content as a table of screenshots
> (https://github.com/szymonwilczek/au-themes/blob/main/README.org), but
> my Org/HTML-fu is not strong enough to understand why.

GitHub renders Org with org-ruby, which still knows only the old syntax.
It treats `#+BEGIN_HTML' as raw HTML, but it would hide a
`#+BEGIN_EXPORT html' block, so the modern form would remove the gallery
from GitHub. The single-line `#+HTML:' keyword works in both, so I have
switched the README to it, and also gave the headings the internal links
point to a CUSTOM_ID. It is now in the repo.

> Can someone shed some light on this (so I can improve `elpa-admin.el` to
> fix the false positives above)?

The messages come from the regexp in `elpaa--doc-html-adjust-auxfiles',
which matched ` src="<img src="' inside the escaped text.

I've attached the patch that requires the attribute to be inside a real
tag (the FIXME next to that loop). With my old README it goes from 18
matches to none, and it still finds relative `src' attributes, including
in tags over several lines. It also stops the old regexp from rewriting
escaped text such as `&lt;img src="foo.png"' when a file of that name
exists. Hope this helps.

Ah, thanks for the explanation, I had missed that. On Emacs 31 my
timings grew linearly for the inputs I tried, but I can't rule out a
worse case.

I also found another problem with my regexp: on a tag longer than about
300 KB the [^<>]* part fails with "Stack overflow in regexp matcher".
So please drop that patch.

An alternative that avoids both problems is to stop matching attributes
with a regexp and walk the tags instead: find "<" followed by a letter,
then read the attributes one by one (name, optional =, then a "..." or
'...' or bare value) until ">". Each character is looked at once and
none of the regexps can backtrack over a long span, so it's linear and
doesn't overflow the stack. In my tests it:

- finds nothing in the HTML from my old README and nothing in the new
  one,
- still finds relative src values in tags spanning several lines, with
  single quotes or no quotes, and when another attribute's value
  contains ">",
- skips escaped text like &lt;img src="foo.png", and src= inside another
  attribute's value,
- takes 0.01 s on a 1.6 MB data: URI and grows linearly elsewhere.

But of course, it has some limits:

- it's about maybe 20 lines of code instead of one regexp,
- it isn't a real HTML parser: it doesn't skip the contents of <script>,
  <style> or <!-- comments --> (but neither does the current code),
- as you said, nobody has hit a real false positive yet, so it only
  fixes a problem that doesn't exist in practice so far.

If you think it's worth it now, or once a real case shows up, I'm happy
to send it as a patch. If not, no problem.

Thanks,
Szymon
