> > What is "the predicate for identifier completion"?
> 
> It is the predicate that will be used with 'completing-read' (the 
> PREDICATE argument) when an identifier is read with completion (e.g. 
> during 'C-u M-.').

One problem with this PREDICATE business is that the completion
infrastructure passes only the candidates to the predicate function,
whereas here we need to also pass the KIND.  This is very
inconvenient, and sounds like an omission in the design: a backend
that supports many KINDs is expected to gazillion separate functions,
one each for every KIND.  It almost sounds like the design assumes
that a backend knows the KIND just by looking at the identifier, which
is correct in Lisp, but not in general.

There are various hacks and kludges to get around this (I used
apply-partially), but I hope we will be able to find a cleaner
approach, which will also speed up the completion as a nice
side-effect.  IMO, it is not an incident that Eglot doesn't provide
such a predicate.

Another problem which surprised me a bit can be reproduced as follows:

  emacs -Q
  C-x C-f src/dispnew.c
  C-u M-g M-.

This signals an error, evidently because Emacs doesn't yet have a
suitable backend activated/known (and therefore etags.el is not yet
loaded)?  I need to visit-tags-table to get around this.  I think we
need a smarter initialization.

A similar problem exists with
xref-backend-identifier-completion-ignore-case: it doesn't receive
enough information to DTRT.  Evidently, the assumption is that a
backend supports only a single programming language, or a small set of
similar ones, so that they all are either case-sensitive or
case-insensitive.  But that assumption is not true for a backend such
as etags, which supports many different languages, each one with its
own case-sensitivity.
