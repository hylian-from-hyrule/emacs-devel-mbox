Hmm, if we ran the hook a bit later, then it could use (plist-get 
eww-data :dom) to get the DOM. That would actually be quite close to 
what Tyler originally proposed.

I'm not totally sure which way is the best. I think the answer might be 
clearer if we have an answer to the following related question...

EWW has a function called 'eww-reload' that (you guessed it) reloads the 
current page. However, it has a unique feature: if you pass non-nil for 
LOCAL (or use a prefix arg interactively), if only re-renders the page 
using the cached DOM.

Here's the question: if we load a page, change our new hook, and 
locally-reload, should we get the page as it was originally displayed? 
Or should we get a potentially-new DOM as transformed by our hook? (For 
context, local-reload exists to support rewrapping text if you change 
the window size[1], though I'd argue that if you wanted that today you 
should just enable 'shr-fill-text'.)

Sites like YouTube don't want tools like yt-dlp to work, so they
obfuscate the way the browser can download the video.  I already into
this in my previous message, but to bring it up again, this is
effectively a puzzle encoded in JavaScript syntax that you solve by
evaluating the code.  There is no question of freedom to be exercised
here, since this is not a program you can meaningfully modify or use
where any of the four freedoms would matter.  So in the end the user has
three options:

1. Evaluate the JavaScript code to decode the necessary information to
   download the video and watch it on your own terms.

2. Watch the video in a browser, using a _lot_ more non-free JavaScript
   and one day perhaps depending on a non-free browser like Google Chrome.

3. Not watching the video at all.

There might be a forth option: Pointing yt-dlp to use proxy websites
like https://invidious.io/ that decode this puzzle for you allowing you
to watch the video without having to decode/evaluate anything on the
client side.  Since this uses the same underlying program, it is just a
matter of configuration for the user to point the Emacs to download
videos via a proxy instead of youtube.com, thus avoiding the need to
solve the JavaScript puzzle.
