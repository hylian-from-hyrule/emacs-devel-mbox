Richard Stallman rms@gnu.org wrote:

>Is this program a major mode?

Not a mode at all, it's a convenience function for folks who frequently use the `xc' program installed on their systems. Instead of creating a term buffer and running `xc <task>', the user runs M-x xc RET <task> RET and the task immediately runs in a new term buffer. The user is offered completing-read for <task> based on the available options, another convenience.

Before I wrote xc.el I was using compilation-mode, eg to run `xc build' repeatedly. xc tasks may include user interaction which would not be appropriate for compilation-mode, so I chose to run tasks in a term-mode buffer. I love how you can bury a finished compilation buffer with "q" so I replicated that for these xc task buffers.

This is compatible with Markdown and org-mode files, which are commonly used to author READMEs; but it does not depend upon those modes.

>There are many kinds of scripts; which kinds does
xc deal with?

xc uses the term "script" in the generic sense of some list of commands, and perhaps other control information, to be executed (interpreted) by a shell or other command interpreter. xc scripts are typically shell scripts, but could be Python, Lua, or whatever else the user deems appropriate.

xc runs task scripts by locating a "Tasks" headline in the README and a subheadline corresponding to the chosen task, extracting the code in the first code block under that subheadline, then interpreting the extracted code in-process using a default shell or some other process specified by the code's shebang line.

>The description of this Emacs package should state prominently and
explicitly what he page about xc fails to say.

I will push a new version of the xc.el README and in-source remarks to include this context, and later I'll also follow-up with xc upstream to improve the content of xcfile.dev for all users.

> Completion, as implemented for this backend, is very slow, especially

> because it has quadratic behavior: for each candidate, it examines all
> the possible completions, and filters the candidate out if none of the
> completions match KIND.  If you type nothing and just press TAB, it
> will take forever for a large enough project (such as Emacs).
> Improvements are welcome.

I have now pushed an update in commit f982de03ff1 which uses a different 
strategy, seems snappy in Emacs, and somewhat usable even in a larger 
project (but that might depend on the chosen kind).

The approach is to take the corresponding MUST-MATCH regexp from 
etags--types-regexp-alist and search for every occurrence of it in the 
tags file buffer. Whenever matched, apply MUST-NOT-MATCH as well, and 
extract tag names into a hash table - just one pass over the file. Then 
use the hash table in the completion predicate.

TBF I've tried a couple of lighter changes first (e.g. skipping some of 
the heavier parts of your etags--kind-predicate, or stopping at first 
match), and that didn't work - alg complexity was still prohibitive.

I've also benchmarked this against the alternative of adding KIND to the 
arguments of the method xref-backend-identifier-completion-table, and 
the difference seems small enough to keep the current convention.

The new code doesn't include per-file case-fold-seach detection yet, 
sorry for that step back, but it seems compatible with the solution, to 
be added later. At least kind identifier completion seems usable now. 
Feedback welcome.

You mean, to have it filter by KIND?  That's possible, but it's used

What is "the current project"?  These kinds are relevant to Ada and
other languages which etags supports.

> At first I was going to suggest per-mode kind->regexp settings, so that 
> the list of kinds is specific to each language, and we don't show 
> elements that won't fit the current file's language. But it seems 
> antithetical to how you intent to use this (one global index for all 
> different languages in a project).

Per-mode was how it started, but I quickly realized that it was not
useful, because the mode of each file is not known to etags and
determining it is not easy (see the comments I left behind in
etags--keywords-case-insensitive-p, which suffers from the same
problem).  So looping over the list of candidate tags will need to
access the file name of each tag, then look for the relevant regexp.
Moreover, completion of KINDs would need to construct a single list
from mode-specific lists, which is extra work.

single list is such a bad idea, don't you agree?
