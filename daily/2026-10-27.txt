> Hold on here!  Please, someone, post a brief description (10 lines or
> 20) of what job this package does, followed by its introductory
> documentation.

`xc.el` is an Emacs front end for `xc`, a task runner that takes its 
commands out of a README.

In a project using `xc`, each task is a heading with a fenced code block 
under it, in `README.md` or `README.org`. The name of the heading is the 
name of the task, and the code in the block is what gets run. The point 
is that the docs and the scripts are the same file, so the steps people 
read are the steps they run. A `Makefile` and a README drift apart 
because they are two separate things. Here they cannot.

`M-x xc` asks `xc` for the task names in the README of the current 
project, offers them for completion, and runs the one you pick in a 
term-mode buffer. The buffer scrolls to the bottom as output arrives, 
and `q` closes it once the task has finished. Nothing is run through a 
shell: the package calls the `xc` executable directly with 
`call-process`, and warns if `xc` is not on the PATH.

Examples:
---------

Markdown, the basic case

     # Tasks
     ## build

     Builds the binary.

     ```
     go build ./cmd/xc
     ```

So the comand `go build` would be executed by the xc.

Org mode
----------

     * Tasks
     ** deploy
     Sends the site to the server.
     #+begin_src sh
     rsync -a public/ user@example.org:site/
     #+end_src

so the rsync command above would be executed.

Introductory documentation

An extract from the header of `xc.el`:

     ;;; xc.el --- Emacs interface for xc  -*- lexical-binding: t; -*-

     ;;; Commentary:
     ;; An Emacs interface to the xc task-runner, <https://xcfile.dev/>
     ;; Use `xc' to launch a task defined in your README

     ;; The common use case for `xc' is to run build, test, deploy type 
commands
     ;; that are documented in your README. Putting the documented steps 
on
     ;; the ``hot path'' ensures they don't get out-of-date and aids in
     ;; discoverability. A unique feature of `xc' is that it supports 
both
     ;; Markdown and org-mode READMEs.

 From `README.org`:

     * To use

     - =M-x= xc =RET= task-name =RET= \
       Runs the given task. The set of available tasks is offered for 
completion.

     - In Treemacs, a project with =xc= tasks in its root README will 
show an =[XC TASKS]= list in its tree. To run a task, double-click it, 
or move point to your desired task and press =RET=. See the action shot 
above for an example, and "Configuration" below for instructions to 
enable the Treemacs integration.

     #+begin_src elisp
       ;; Recommended: bind to keyboard
       (bind-key "C-c x" #'xc)

       ;; If you use Treemacs, initialize the integration:
       (with-eval-after-load 'treemacs
         (require 'xc-treemacs))
     #+end_src


> Also, how does 'xc.el' relate to `xc'?

See above.

Example:

$ xc deps
+ ls -1
README.md
README.org
sub
tagged.org
+ echo '3 tasks in this README'
3 tasks in this README

by running `xc` program, it gives possible tasks for execution that were 
defined in README files.

So Emacs command shows xc outputs in the buffer, with completion of task 
names, tasks defined in README, and executes such.

app-editors/emacs Gentoo ebuild. On Gentoo, I had to enable libxml2
explicitly.

default?

To give more details, I became aware of the unwanted HTTP requests
through the `gnus-html-wash-tags' function in gnus-html.el:

(gnus-message 8 "gnus-html-wash-tags: fetching link URL %s" url)

After enabling libxml2, these messages stopped. Also,
`gnus-html-wash-images' contains

(gnus-message 8 "gnus-html-wash-tags: fetching image URL %s" url)

I don't recall seeing these particular messages even with image loading
enabled.

Right now, I have no idea if these are the only two channels through
which the requests go. Only a network tool can say for sure.

Thus, turning libxml2 on by default seems reasonable *pending further
review*.
