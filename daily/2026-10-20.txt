Subject: The Kitty Keyboard Protocol and C-g
Message-ID: <87v76whhor.fsf@athena.silentflame.com>
In-Reply-To:

The Kitty Keyboard Protocol[1] is a new way for terminal emulators to
communicate user input to text mode applications, like xterm's
modifyOtherKeys that we already support, but with several more
enhancements such as distinguishing between key-down and key-up events,
and disambiguating more possible key chord presses.

It's also already widely implemented in terminal emulators (alacritty,
foot, ghostty are some big names on GNU; on non-free platforms, macOS's
iTerm2 and Microsoft's terminal application implement it) as compared
with just Xterm for modifyOtherKeys.

I'm planning to implement KKP for Emacs.  I'll work from the
implementation of modifyOtherKeys, so I don't expect anything to be
difficult or controversial, except for one thing: KKP means that C-g
arrives as a multi-byte sequence, and that means we can't register it as
the controlling tty's VINTR and VQUIT like we do at present.

Essentially this means that with KKP enabled, C-g in a 'emacs -nw' frame
will be like C-g in an 'emacsclient -t' frame: it can still interrupt
Emacs, but only at the next maybe_quit, via the SIGIO route.
The (info "(emacs)Emergency Escape") mechanism would become unavailable.

I think this trade-off is acceptable and KKP should be turned on by
default.  We can document the issue, and users can always turn off KKP
support in favour of keeping emergency escape.  I predict that most
people would prefer to have C-. and C-, work without any specific
configuration in their text mode frames.

I did try asking about extending KKP so that it doesn't rule out use of
VINTR etc. but this did not receive a warm reception.[2]

[1]  https://sw.kovidgoyal.net/kitty/keyboard-protocol/
[2]  https://github.com/kovidgoyal/kitty/issues/10704
     (non-free javascript only, unfortunately)

-- 
Sean Whitton
