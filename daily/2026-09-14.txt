For a while now I've been running the pgtk build of Emacs with the 
following wrapper bash function:

$ type emacs
emacs is a function
emacs ()
{
     if [ "$XDG_SESSION_TYPE" = "tty" ]; then
         command emacs -nw "$@";
     else
         command emacs "$@";
     fi
}

With this wrapper script, pgtk Emacs builds can detect that there is no 
windowing system available and start up in terminal mode when I'm 
running a remote Emacs in an ssh session.  This was previously a big 
annoyance with the pgtk build.  Would it be safe to make this check part 
of Emacs proper?

Do you mean that 'completing-read' should support KIND explicitly? How?

Kinds are introduced by xref, and don't have a meaning for completion in 
general, so at best is would be a &rest kind of argument, passed 
verbatim to the predicate, or something like that. Does not seem worth it.

> This is very
> inconvenient, and sounds like an omission in the design: a backend
> that supports many KINDs is expected to gazillion separate functions,
> one each for every KIND.

It doesn't have to, it could instead return a common anonymous function 
which would make the decision based on the lexically captured value of 
KIND. That is what happened in elisp-mode.el before commit 2daeb3ca35.

The current implementation seems more efficient to me, but performance 
tradeoffs might not matter in your scenario, measurements needed.

> It almost sounds like the design assumes
> that a backend knows the KIND just by looking at the identifier, which
> is correct in Lisp, but not in general.

No more than it assumes that the backend knows the list of definitions 
for that identifier "just by looking".

Indeed it might be harder to do for some backends than others (so Eglot 
does not have a predicate, and I assumed it might be a pain to do for 
etags too), but those limitations seem natural.

> There are various hacks and kludges to get around this (I used
> apply-partially), but I hope we will be able to find a cleaner
> approach, which will also speed up the completion as a nice
> side-effect.

I'm not sure how you see it working better. 
xref-backend-identifier-completion-predicate designed as returning a 
predicate function has a chance to take the value of KIND and 
pre-populate any caches it needs and return a appropriate function.

If the cache is in a local variable (e.g. hash table), the returned 
value will need to be an anonymous function. If the cache is in a global 
variable, then one of the named functions could be returned. Using 
'apply-partially' does not get around it, and does not print any nicer 
function literals in backtraces, unfortunately.

> IMO, it is not an incident that Eglot doesn't provide
> such a predicate.

For Eglot it's a consequence of what the LSP protocol can and cannot do.

I don't think Emacs cares about the XDG_SESSION_TYPE variable. I tried the
following:

env XDG_SESSION_TYPE=tty emacs
env XDG_SESSION_TYPE=x11 emacs
env XDG_SESSION_TYPE=wayland emacs
env XDG_SESSION_TYPE=oatmeal emacs
env -u XDG_SESSION_TYPE emacs    # Unset the variable.

Here Emacs is started as a Wayland app regardless of the value of the
variable. Also, the value of XDG_SESSION_TYPE only tells what the local
display server (if any) provides, but it should not hinder you from setting
the DISPLAY variable to point to some display server elsewhere, as is done
with ssh combined with X forwarding, or with Waypipe. Therefore I think the
XDG_SESSION_TYPE is a bad choice to determine whether you want to start
Emacs in text mode or not.

A better alternative would be for Emacs to examine if both the DISPLAY and
WAYLAND_DISPLAY variables are unset, and if that is the case, start Emacs
in text mode. Currently, at least for me, PGTK Emacs refuses to start with
the warning "cannot open display".

If your PGTK build does not display the warning and starts in text mode
without the -nw option, there must be something different with how your
Emacs is built, or maybe different versions of GTK3, or something different
about the environment where it is started. Here PGTK Emacs (configured
simply with "--with-pgtk") does not automatically fall back to text mode.

The caller of the predicate function doesn't know the KIND of
a candidate (it's infrastructure code which passes strings around
without any idea of what they might mean), so only the predicate
function can know it and compare it to the desired KIND (the one passed
earlier to the generic function).

>> But, as for the completion-ignore-case, I tend to lean towards filtering
>> for KIND in the completion-table rather than via the predicate.
> In the case in point, the completion-table is a large heap of strings,
> each one of which comes from a different file with potentially
> different case-sensitivity (as determined by the major-mode of that
> file).  How can such a completion-table know which candidate needs to
> be compared case-sensitively and which case-insensitively?

If some parts of your completion table need to be matched
case-sensitively and other parts case-*in*sensitively, then clearly the
caller of the completion-table is not in a position to decide because
it sees the completion table as a single object with
table-wide operations.

This said, AFAICT, in 99% of the desired case-sensitivity depends mostly
on the major mode (and potentially also on the KIND of the desired result of
that completion): any candidate that comes from a file that uses
different case-sensitivity is usually a bad candidate anyway (it's very
unusual to want to complete a C variable name from an identifier found
in a Common Lisp file, for example).
